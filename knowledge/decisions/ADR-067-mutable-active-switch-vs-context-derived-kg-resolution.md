# ADR-067: Mutable `.active` switch vs context-derived KG resolution — decision pending

**Date:** 2026-07-15
**Status:** Proposed — **design agreed 2026-07-26, then reviewed three times by two independent models (Opus twice, Fable once, all 2026-07-26/27).** All 22 Opus findings (14 original + 8 second-scan) have a resolved *direction* recorded (see § Opus Review Findings, § Round 2/3 Brainstorm, § Live Split-Brain below), but a follow-up Fable review (§ Fable Review Findings, 2026-07-27) found the true open count is larger than that made it sound: **3 mechanisms are explicitly agreed-but-undesigned** (registry concurrency/locking, personal-scope marker syntax, moved-path compare-view), **1 field's disposition was never decided** (`lastUsed`), **1 previously-"resolved" item needs revisiting** (item 7's blanket nested-KG ban — real pushback on monorepo/workspace use cases), **2 already-resolved items were never cross-checked against each other** (Round 3 items 4 and 8 — no precedence rule for "stay in personal" vs. a cwd change), and **6 new use cases** surfaced with no existing coverage (CI/non-interactive callers, cached-registry staleness, subagent scope inheritance, session-resume-after-restart, accidental duplicate registration, bulk cross-registry browsing). **Not yet implementation-ready** — these need their own brainstorming pass before a plan is written. Still no branch, no code changes.

## Context

Raised 2026-07-15 while reviewing the issue-14 config-path fix. This is a **future architectural question**, captured so it is not lost. It is **not** part of issue-14 and does not gate c1/c2/c3.

### The current model

KMGraph resolves "which knowledge graph am I operating on" through a **single mutable pointer**: `kg-config.json` holds an `.active` field, `/kmgraph:kmg-switch` rewrites it, and every tool/command reads `.active` to pick the target KG. This is **global mutable state** — one active KG at a time, shared across all sessions and all projects on the machine.

### Why this is being questioned (the bleed risk)

A single mutable `.active` pointer has structural failure modes where a correct path string still routes an operation to the wrong KG:

1. **Stale/divergent pointer** — the exact split-brain issue-14 is fixing: `.active` written to one config file, read from another. More generally, any staleness in `.active` sends a write meant for KG-A into KG-B.
2. **Concurrency** — two Claude Code sessions (or two projects) open at once share one `.active`. Switching in session 1 silently changes the target for session 2 → cross-KG contamination ("bleed").
3. **Context mismatch** — the active KG can disagree with the current working directory / project. (Prior art: issue-10 added a `getProjectRoot()` / `KG_MISMATCH` guard that *detects* active≠cwd, i.e. the project already treats this mismatch as a hazard worth guarding.)

### The alternative under consideration

Instead of a mutable toggle, resolve the KG from **context** — derive it from the project root / working directory (and/or an explicit per-invocation argument), the way the context-mode plugin centralizes context resolution. This would make "which KG" a function of *where you are*, not a stateful global flag, structurally eliminating failure modes 1-3.

### Interaction with in-flight work

- c1 (issue-14) fixes `kmg-switch`'s config path **now**; that fix is correct regardless of this decision (the switch still writes to the right file in the interim).
- If a future decision **replaces** the mutable-switch model, the `kmg-switch` command (and its c1 fix) would be **superseded**, and the resolution logic across every `kg_*` tool and command would change. This is a large blast radius — hence a dedicated ADR, not a patch.

## Prior Art (recall + chat-history sweep, 2026-07-15)

A recall + `knowledge/chat-history/2026-02/` sweep was run before framing this decision. Findings:

- **Separation itself was never a reasoned decision — it is an unexamined premise.** `ADR-001:16` ("designed to support multiple independent knowledge graphs, each potentially owned by different users or projects") and `ADR-001:28` assume separation; no ADR argues isolation/privacy/anti-bleed as the reason to keep graphs separate. Ironically ADR-001's stated *problem* was the opposite — **fragmentation** (too separate, no coordination), not bleed. Any isolation rationale this ADR needs must be **authored**, not quoted.
- **The `.active` + switch model was deliberate — but weighed only against config-file alternatives, not against context-derived resolution.** `ADR-001:85-95` (Alternatives Considered):
  - **Option A — per-project `.claude/kg-local.json` (self-contained, the closest proxy to cwd/context-derived):** *rejected* — "Can't switch between KGs; must edit per-project config to use global KG." I.e. it could not serve "different KGs for different tasks" or reach a global/cowork KG from inside any project directory.
  - **Option B — env var `KG_PATH`:** rejected (fragile, no discovery).
  - Positive rationale (`ADR-001:80-83`): single source of truth; **git-like active-pointer pattern**; extensible; backward-compatible.
- **Pure context/cwd-derived resolution was never proposed before this ADR (2026-07-15).** ADR-001 foreclosed it structurally without naming it.
- **`ADR-060` already characterized the switch as intentionally manual, contrasting context-mode.** `ADR-060:35` was "Prompted by a user question ('recall why we switch KGs manually and context-mode doesn't')"; `ADR-060:29,59` frame ADR-001's model as **"manual/git-like, not auto-detected like context-mode's project scoping"** — serving intentional, durable knowledge management. This is the strongest "it was intentional" citation (though ADR-060 interprets ADR-001's intent after the fact; ADR-001 never wrote "we rejected auto-detection").
- **The Option-A rejection reason is still live** — a cwd-bound model has no home for the personal/global/cowork cross-project KGs that are intentionally *not* tied to a directory. This is precisely open question #2 below, and it pushes the answer toward a **hybrid** (context-derived default + explicit override) rather than a clean replacement of the switch.
- **Bleed has a concrete track record that favors revisiting:** `ADR-019` (v0.2.0-beta) first named the wrong-graph-write hazard and added an agent-instruction write guard; the data-layer `KG_MISMATCH` guard (`kg_capture`, issue-10) was meant to harden it but shipped as a **false-positive bug** ("currently more friction than protection", `issue-10-description.md:31`); and issue-14 is the live split-brain. The mutable-pointer model has now produced **two distinct real bugs** where correct-looking state still routed to the wrong KG — direct evidence for the failure modes in the Context above.

## New Incident + a Working Mitigation, Observed Live (2026-07-21)

A third real drift incident, on the `v0.6.20-storage-migration-completion` branch: `.active` was confirmed correctly pointing at `knowledge-graph` earlier in the same session (checked directly before running `kg_upgrade` operations), then found — later in the same session, no `kmg-switch` call in between — pointing at `docs-readme-poc`, a completely unrelated project. Root cause not investigated (out of scope for the in-flight branch); the point is the drift happened silently, mid-session, exactly as failure mode 2/3 above predict, with no action taken by the user or the assistant to cause it.

**What explicitly did NOT go wrong, and why — this is the useful part.** Two background agents were writing real content to `knowledge-graph`'s own `knowledge/sessions/` and `handoff-packages/` during this exact drift window. Neither wrote to the wrong project. Both were given an **explicit absolute working directory** and **explicit relative file paths** in their task prompts, and used direct file Read/Write/Edit tools — never a `kg_*` MCP tool, which is the only thing that actually resolves against `.active`. The active-pointer's value was simply never consulted for these writes; the operation was anchored to an explicit path from the start, not resolved from ambient state.

**This is a concrete, observed data point for the open decision, not just a hazard restated:** explicit-path / context-anchored operations are *structurally immune* to `.active` drift, by construction — not because they're careful, but because they never ask the question `.active` answers. This is direct empirical support for the "context-derived resolution" side of question 1 below, and independently, a viable *interim* mitigation while the ADR stays undecided: prefer giving agents/tools an explicit target path over relying on implicit active-KG resolution, whenever the target project is already known. Worth weighing explicitly when this is picked up — not as the final answer (it doesn't address the cross-project personal/global KGs that have no cwd, per question 2), but as evidence of which failure modes an explicit-path convention already closes today, without waiting on this decision.

## Decision

**PENDING — not yet decided, and deliberately deferred beyond the current session.** Questions to resolve when this is picked up:

1. **Do we keep the mutable `.active` switch, or move to context-derived resolution** (project-root/cwd-based), or a hybrid (context-derived default + explicit override)?
2. If context-derived: **how is the KG chosen when cwd maps to no registered KG**, or to more than one? What replaces the "personal / global / cowork" cross-project KGs that are intentionally *not* tied to a cwd?
3. **Concurrency semantics** — is "active KG" per-machine, per-session, or per-project? (The bleed risk is fundamentally about this scope.)
4. **Migration path** — how do existing installs relying on `.active` + `kmg-switch` transition without breaking? What happens to the `kmg-switch` command and its issue-14/c1 fix?
5. **Relationship to issue-10's `KG_MISMATCH` guard** — does context-derived resolution subsume it, or coexist?

_No option selected. Consequences, migration design, and cascade impact across all `kg_*` tools, commands, and the switch surface are deferred until the decision above is made._

## Brainstorm Session Findings (2026-07-21) — spec-in-progress, decision still PENDING

A `/superpowers:brainstorming` session on this ADR produced the following. **This is design-in-progress captured for continuity, not a decision** — status remains Proposed/pending.

### User's stated bottom line (verbatim intent)

"Having one authoritative graph that is constantly switching is not going to work. Users work on multiple projects simultaneously and should not have to think about which graph is active. If a user is in one repo/folder in one terminal session, the graph should know to write/read from that one. If there is a parallel session working in a completely different repo, the user should read/write from that one without having to think about it. There should be no bleed between them. The only overlap might be both being able to read the user-level graph which goes across all local projects. Each session might even be in different LLMs — one in Claude, another in Codex, in a different repo."

This resolves Q1's direction: **no mutable `.active` switch** as the default resolution mechanism. Replace with **stateless, context-derived (cwd/project-root) resolution per call** — no shared file is read as "current truth," so concurrent sessions (even across different LLM tools) cannot bleed into each other by construction, because there is nothing shared to drift.

### Emerging Q1 model (not yet finalized)

- **Project-local KG**: auto-resolved from cwd/project-root at call time, no switch needed. Candidate mechanism: promote issue-10's existing `getProjectRoot()` from a mismatch *guard* to the actual *router*.
- **Personal KG** (singular, cross-project): always reachable regardless of cwd, addressed via an explicit param on the call (not a global switch) — e.g. `scope: "user"` — rather than a stateful toggle.
- **Agent-level judgment on when to search which scope** (e.g., search project by default, offer "want me to check your personal KG too?" as a follow-up rather than hard-coding a merged-search default) is explicitly **out of scope for this ADR** — flagged as a question for the fable/planning pass, not an architectural rule.

### Research findings that complicate/refine the model (agent sweep of chat-history + KG + live config, 2026-07-21)

1. **Historical switch usage was project↔project only, never project→personal.** All 18 real `kmg-switch` invocations found in `knowledge/chat-history/` (2025-12 through 2026-07) swap between project-local KGs (e.g. `knowledge-graph` ↔ `docs-readme-poc`). No instance of switching to a personal KG exists — because none has ever been created on this machine, despite ENH-001 "completing" the code path in 2026-03. This *strengthens* the case for killing the switch: the actual historical pain (project↔project switching) is exactly what cwd-derived resolution eliminates.
2. **A live split-brain instance exists right now, in this repo, at the moment of writing.** `~/.kmgraph/kg-config.json` currently reads `active: docs-readme-poc` while cwd is `knowledge-graph`. A second, stale legacy copy at `~/.claude/kg-config.json` reads `active: knowledge-graph`, frozen mid-migration since 2026-07-17 (`lastAppliedVersion: 0.3.10`). This is the exact drift class this ADR already documents (the 2026-07-21 incident, above), caught live rather than reconstructed after the fact.
3. **Only 2 KGs are registered today, both `project-local`** (`knowledge-graph`, `docs-readme-poc`). No `personal` or `global-topic` KG exists yet on this machine.
4. **The real taxonomy is three shapes, not two.** ADR-066 (resolved 2026-07-17, not yet implemented as of the v0.6.20 plan) kills `cowork` as a KG type but keeps **global-topic KGs** as a separate first-class concept: arbitrary count, user-named, stored at `~/.kmgraph/knowledge-graphs/<name>/`. So the model is **project-local (many, cwd-resolved)** + **personal (exactly one, singular)** + **global-topic (many, named)**. The emerging Q1 model above only accounts for project vs. a single "user-level" scope — it has **no answer yet for selecting among multiple named global-topic KGs**, which is likely Q2 territory (what happens when cwd maps to none/multiple candidates) rather than a Q1 concern, but is flagged here so it isn't lost.
5. **Two live bugs in the current write path that any new resolution model must not silently inherit:**
   - **issue-15**: `capture.ts`'s `rebuildIndex()` never passes `kgType`, so writes targeting a `personal` KG get indexed under the `project-local` FTS5 bucket.
   - **issue-27**: `applyStrayKnowledgeDir()` silently overwrote real KG content by skipping a destination-exists check — reinforces that any new resolution logic needs an explicit "never silently overwrite/misroute" invariant (ADR-063 pattern).

### Fable Review (2026-07-21) — independent second opinion, requested mid-brainstorm

Fable (`claude-fable-5`) was given the emerging model above plus the research findings and asked for (a) a recommendation on global-topic KG selection and (b) any gaps in the model not already surfaced. Response:

**Recommendation — registry lookup + mandatory disambiguation, not keyword-match or MRU.** Require an explicit `topic` param on every call, resolved via a registry/manifest lookup (list of topic-KG names + short descriptions) *before* the call: the tool exposes a lightweight list/lookup, the assistant performs one resolution pass (exact name match, or fuzzy match against name/description), and only passes the param once confident. If zero or multiple candidates match, the tool refuses and forces the assistant to ask the user rather than guess.

*Alternatives considered and rejected, per Fable:*
- **Keyword/topic matching as the sole mechanism** — risks exactly the failure class being eliminated: silent misdirection, just non-deterministic instead of stale-pointer.
- **Most-recently-used heuristic** — definitionally the same bug pattern as `.active` in a different hat: implicit shared state that drifts.
- **Pure "always ask the user"** — safe, but degrades UX for the common case where the assistant can resolve unambiguously (e.g., user said "log this under woodworking" and only one KG matches).
- The registry approach gets assistant-side confidence *and* keeps writes deterministic and explicit. Reads can be more permissive (fan-out across matches is low-risk); writes cannot.

*Stated failure mode of its own recommendation*: depends on the assistant actually performing the lookup step every time. Under time/context pressure an assistant can skip the list-and-match round trip and pass a remembered or hallucinated topic name directly. If that name doesn't exist, the result is a clean error (safe). If it's a near-miss of an existing name (typo, pluralization, stale name after a rename), the result is a misdirected write that looks superficially fine — the same class of silent-wrong-target bug, just moved from "shared mutable pointer" to "assistant's guess," and harder to detect because there's no drift signal to notice. Mitigation: the tool should always echo back the resolved KG name/description in its response, so misdirection is at least visible to whoever reads the result, even if not structurally prevented.

**New gaps identified (beyond what this ADR had already surfaced):**

1. Read/write need explicitly different resolution defaults (fan-out-merge for search, never for capture), not one shared algorithm with variable strictness.
2. The registry itself is new shared mutable state, same failure class as `.active`, just narrower scope — must stay append-mostly and never grow a "current"/"last used" field, or the bug reappears one layer down.
3. First mention of a brand-new topic name is a *creation* decision, not a *selection* one, and needs its own gate.
4. Namespace collisions are unhandled: nothing stops a topic-KG name from colliding with a project directory name or the reserved "personal" scope.
5. The known indexer bug (issue-15, missing `kgType`) is a symptom of implicit/positional scope-tagging generally, not a one-off — the fix needs to make type an explicit required tag at write time everywhere, or the same bug recurs for topic KGs.
6. No lifecycle story exists for delete/rename of a topic KG while another session holds a reference to it by name — structurally the same live-reference problem as the concurrent-session bleed being fixed for project-local KGs, but unaddressed for the registry case.

## Cross-Tool Comparison: gh's per-repo identity switching (2026-07-25)

While debugging an unrelated problem in a different session/repo (`docs-readme-poc`) — `gh auth switch` not giving true per-terminal isolation because `gh` reads one shared `~/.config/gh/hosts.yml` regardless of terminal — the user was given this fix by that session's assistant, and asked whether it's applicable to ADR-067. Captured here as a validating data point, not a decision.

**The gh fix, two parts:**
1. `GH_CONFIG_DIR` env var override, pointed at an isolated per-identity config dir (`~/.config/gh-tidal`), set manually per terminal (or via `direnv`/`.envrc`).
2. Optional zsh `chpwd` hook in `~/.zshrc` that auto-sets/unsets `GH_CONFIG_DIR` on `cd` into a specific repo — recomputed fresh every directory change, nothing persisted as "current identity" between calls.

**Assessment: validates the principle, mechanism doesn't transfer directly.**

- Part 2 (chpwd hook) is structurally the same pattern as this ADR's context-derived direction: derive the answer from cwd at the moment of the call, instead of storing it in a mutable pointer that can drift (`.active` / `GH_CONFIG_DIR`-if-forgotten-to-unset). Real independent evidence for "derive, don't store."
- The mechanism doesn't reuse as-is because gh is a plain CLI — each invocation is a fresh process with no way to know "where am I" except reading ambient shell state, so a shell hook is the only lever available. KMGraph's `kg_*` tools are MCP tool calls that already run inside code with direct access to cwd/project-root at call time (`getProjectRoot()`, `mcp-server/src/utils.ts:106`, already wired as a mismatch guard in `capture.ts:254`, per issue-10). Introducing a shell-level env var here would add a new class of persisted state (shell-session-scoped) — the same failure category as `.active`, just relocated, not eliminated.
- Where the two do line up structurally: isolated storage-per-identity (`~/.config/gh-tidal`) mirrors isolated storage-per-project-KG (`~/.kmgraph/knowledge-graphs/<name>/`, per ADR-066) — a storage-layout parallel, not a resolution-logic one.
- Confirms the actual feasibility test for this ADR is promoting `getProjectRoot()` from guard to router inside `kg_*` handlers directly (code already half-built via issue-10), not a shell-hook analog.

Real-world test in progress: user is attempting to get the gh `chpwd`-hook fix itself working, live, in the `docs-readme-poc` session/repo — a separate, unrelated debugging effort, not part of this ADR's implementation.

## External Research (2026-07-26) — industry precedent, still no decision

A web search for prior art on this exact class of problem (global mutable "current selection" state vs. deriving the answer from context per-call), requested explicitly to sanity-check the direction against outside evidence rather than only this project's own history.

**1. `kubectl`'s `current-context` has the identical, well-documented bleed failure.** Multiple independent sources describe the same symptom this ADR names: a second terminal silently picks up a context change made in a first terminal, because `kubectl` reads one shared `~/.kube/config` `current-context` field regardless of which terminal or directory issued the change — structurally the same bug class as `.active`, just a different tool. The ecosystem's actual fix in practice is **not** a better switch command (`kubectx` itself is called out as still carrying the same global-mutation risk) — it's abandoning the shared pointer for either (a) `KUBECONFIG` env-var scoping per project, or (b) `direnv`, which loads/unloads directory-scoped state on `cd` with "variables never leak" as the explicit design goal. This is real-world confirmation that the "derive from context, don't store a shared pointer" direction already adopted above is the field's actual converged answer to this exact failure mode, not a novel or risky choice.

**2. The MCP protocol itself is moving to statelessness in days, not years.** The 2026-07-28 MCP specification release candidate (SEP-2567, SEP-2575) removes the `initialize` handshake and the `Mcp-Session-Id` header entirely — every request now carries its own context in `_meta`, with no persisted session state and no sticky-routing requirement, specifically because "the Model Context Protocol's session-based architecture has been a production liability." KMGraph's `kg_*` tools are MCP tool calls running on this exact protocol. This lands directly on Q1: promoting `getProjectRoot()` from a mismatch guard (issue-10) to the primary per-call router isn't just internally consistent with this project's own evidence — it's the same architectural direction the protocol layer underneath it is independently taking, for the same underlying reason (a shared session/pointer is a liability; a self-describing per-call request is not).

**3. Multi-tenant MCP isolation guidance converges on explicit-scope-per-call, never inferred from shared state** — consistent with, not a new input to, the registry-lookup + mandatory-disambiguation direction already adopted above for personal/global-topic KG selection.

**Assessed scope of findings 1+2 — validates one half of the model, does not replace the other half.** Both findings are strong, independent confirmation for the **project-local** resolution case (cwd-derived, stateless, per-call) — which is also the empirically dominant case (all 18 historical `kmg-switch` invocations were project↔project). Neither finding has an analog for **personal KG** (singular, no cwd to derive from) or **global-topic KGs** (multiple named candidates; cwd carries no signal about which one is meant). `direnv`/`KUBECONFIG` scoping and the MCP stateless spec both solve "know where you are," not "pick one of several named things with no locational signal" — so they cannot substitute for the registry-lookup + mandatory-disambiguation mechanism (Fable's recommendation, § Brainstorm Session Findings above) for that second case. Adopting only findings 1+2 and dropping the registry-lookup piece would silently leave personal/global-topic KGs unresolved — the same shape of gap Option A was rejected for in ADR-001's original alternatives analysis. **Conclusion: findings 1+2 confirm and strengthen the project-local half of the emerging model; they do not replace the explicit-param/registry-lookup half, which stays in the model.**

## v0.7 Brainstorm Session — Resolved Design (2026-07-26)

A `/superpowers:brainstorming` session, run against `docs/specs/2026-07-26-adr-067-kg-resolution-v0.7-spec.md` (written earlier the same day for cross-model review), worked through every open question in that spec's §4 one at a time with the user. **This resolves the design** — status below moves from "no decision" to "design agreed, not yet implemented." A separate implementation-ready design doc will be written to `docs/superpowers/specs/` per the brainstorming skill's normal flow; this section is the durable record so nothing here is lost regardless of what happens to that doc.

### Scope correction: two KG shapes, not three

Global-topic KGs (ADR-066's third taxonomy shape) are **out of scope for this decision**. The project is designed around per-project and per-person graphs today; no real "topic spanning multiple projects" use case has been observed. Captured separately as **ENH-053** rather than designed for speculatively. This simplifies the model to exactly two shapes:

- **Project-local** (many) — resolved from cwd/project-root, per call.
- **Personal** (exactly one) — the thing "my graph"/"user graph"/"personal"/"personal graph" all refer to, interchangeably; lives outside all repos in `~/.kmgraph/`. Resolved via an explicit `scope` param, not a switch.

### Resolution flow (resolves Q1 and the registry-lookup question)

1. **No name given** → resolve from cwd/project-root, silently, no confirmation. This is the default path and the empirically dominant case (all 18 historical `kmg-switch` invocations were project↔project). **⚠️ Text not yet updated to reflect later carve-outs (Fable review, 2026-07-27):** this step's "silently, no confirmation" is no longer true without exception — item 12(a) (§ Opus Review Findings) requires explicit confirmation on a first-time-seeing-this-repo write, and § Round 3 item 4 requires a one-time flag when cwd has changed since the last call. Both are compatible with this step's intent but the text here was never edited to say so.
2. **Name given, exact match against the existing `graphs` registry** (in `kg-config.json` — no new registry construct needed) → route directly.
3. **Name given, fuzzy match(es)** (typo, pluralization, stale rename) → **always** show the candidates and ask which one is meant — no silent fan-out, for reads or writes. (Resolves the read/write-asymmetry open question: there is no asymmetry. Concrete motivating example from the user: `docs-readme-poc` vs. `docs-mintlify-poc` — two real, unrelated POCs on this machine that share a fuzzy prefix; blending their results on a read would be worse than asking once.)
4. **Name given, no match at all** → tell the user it isn't registered. **No search of unregistered locations** — KMGraph only knows about projects that have run `kmg-init` and registered; searching for an arbitrarily-named, arbitrarily-located, arbitrary-VCS folder it has never seen before is unreliable by construction (not all projects live under one folder, not all use git, naming is arbitrary) and was explicitly rejected as a design direction rather than merely left undesigned. (This is distinct from the ordinary, bounded filesystem access step 1 already requires — walking upward from cwd to find which *already-registered* project root it falls under. That's matching against known data, not searching for unknown folders.) If the user means a real project, the answer is "go there and run `kmg-init`," not an automated search.

### Registry lifecycle (resolves the archive/delete open question)

- Existing `graphs` entries gain a lightweight lifecycle: **`status`** (`active` / `archived` / `deleted`) + **`statusChangedAt`** timestamp + optional **`githubUser`** (if applicable) — added to the entry, not a new field on top of it.
- **Archive, don't hard-delete.** Archiving flips status + timestamp only; the KG's actual content directory is never touched (ADR-063 invariant — never destroy known-good state before a confirmed write).
- **Writing to an archived/deleted entry never happens silently** — surface "this graph was archived on `<date>`," offer to restore, before proceeding.
- A **full history log** (every transition, not just current status) was explicitly considered and deferred — YAGNI'd out, captured as **ENH-054** — because nothing discussed needs "how many times has this been archived," only "is it archived, since when, offer to undo."
- This satisfies Fable's earlier-flagged gap (§ Brainstorm Session Findings above, gap #2: "the registry itself is new shared mutable state... must stay append-mostly and never grow a 'current'/'last used' field") — `status`/`statusChangedAt` is a per-entry state field, not a shared "current" pointer, so it doesn't reintroduce the bug this ADR exists to close.

### `kmg-switch` and the `KG_MISMATCH` guard — both retired

- **`kmg-switch` is retired as a config-mutating command in any form**, including a version scoped narrowly to just the personal-graph case. Any disk-persisted "current target" — even small — reintroduces the exact drift risk this ADR exists to close, just with a smaller blast radius. Personal-graph access becomes an explicit `scope` param per call; the "I want to talk to my personal graph for a while without repeating the param" ergonomic need is met by an **ephemeral, in-session-only preference — never written to disk, never shared across sessions**.
- **issue-10's `KG_MISMATCH` guard becomes dead code once this model is live** — there's no separate "active" value left to disagree with cwd, because cwd *is* the resolution. Confirmed explicitly by the user ("if this new framework works the way it is supposed to, then I guess it would make it redundant"). Retire it as part of migration rather than leave it stranded.

### Inherited constraints (not new decisions — existing bugs the new model must not reproduce)

- **issue-15**: `kgType`/scope must be an explicit required tag at every write call, never inferred positionally — closes the personal-KG-writes-misindexed-under-project-local-FTS5-bucket bug.
- **issue-27**: never silently overwrite/misroute — applies to the archived-entry-write case above as much as it did to `applyStrayKnowledgeDir()`.

### Migration path (resolves the last open question)

- Rides the **existing `upgrade-inspector` mechanism** (same one already shipped for the cowork/global-topic migration in v0.6.20) rather than a bespoke script — proven to actually reach users, unlike a migration that only exists as unreached code (see issue-28's dev-loop gap, which is exactly the failure mode a *disconnected* migration script would hit).
- **Explicit, plain-English notice** of the behavior change, **explicit consent** before cutover, **originals backed up** before any destructive step — matching ADR-063 and the precedent already set by the cowork-mode migration. Discussed and explicitly endorsed as the right level of transparency (with real external precedent: `git`'s multi-year `init.defaultBranch` warning-before-enforcing rollout, Kubernetes's deprecation-window + explicit-conversion-tool pattern for breaking API changes — silent behavior changes on anything that affects *where data goes* are the industry's known anti-pattern, not this project inventing new ceremony).
- Reconciles the two currently-divergent config files (`~/.kmgraph/kg-config.json` vs. legacy `~/.claude/kg-config.json`) as part of the same step.

### Newly captured, explicitly out of scope

- **ENH-053** — topic-KGs spanning multiple related projects (not user-graph, not single-project). Descoped from this decision; revisit only if a real use case appears.
- **ENH-054** — full audit-trail history log for registry lifecycle transitions (vs. the lightweight status+timestamp adopted above). YAGNI'd deliberately.
- **ENH-055** — `kmg-capture-router`'s trigger vocabulary misses "future enhancement"/"worth capturing" phrasing entirely (same failure class as the already-documented "Skill Auto-Triggers Miss Process Vocabulary" lesson) — surfaced live when ENH-053 and ENH-054 didn't auto-capture during this same brainstorm.

## Opus Review Findings (2026-07-26) — blocking issues found before implementation

An independent Opus review of the resolved design above (requested specifically to catch what the brainstorm missed, before writing an implementation-ready spec) found real problems, not nitpicks. Two of the most consequential claims were verified directly against the actual code before being recorded here, per this project's own verification-before-conceding standard — both checked out.

**Confirmed by direct code inspection (`mcp-server/src/utils.ts:106-108`, `mcp-server/src/tools/capture.ts:245-266`, `mcp-server/src/tools/config.ts:48,204`):**

1. **`getProjectRoot()` is not a cwd-resolver and was never "half-built" toward being one.** It is `path.dirname(kgPath)` — it derives a KG's root *from an already-known KG path*, and is only ever used to check whether `process.cwd()` falls under an *already-resolved* KG's root (the `KG_MISMATCH` guard). The "promote the existing guard to router" framing throughout the brainstorm (§ Emerging Q1 model, § Resolution flow step 1) is built on a misreading of what this function does. The actual router — cwd/session-context → which registry entry — does not exist anywhere in the codebase and would be new code, not a promotion.
2. **Per-call cwd isn't actually available the way "resolve from cwd" assumes.** `capture.ts` reads `process.cwd()` directly — the **MCP server process's** cwd, fixed once at process spawn, not the calling session's cwd, and it does not change when a user `cd`s in their terminal. This is almost certainly the real root cause behind issue-10's guard shipping false positives. "Resolve per call from cwd" cannot work as literally stated until cwd (or an equivalent session-context signal) is actually transported per call — via client-supplied `roots`, the MCP `_meta` per-request field (SEP-2567, cited earlier in this ADR as *validating* evidence — it is actually an **unshipped dependency**, not confirmation), or an assistant-supplied param (which reintroduces exactly the assistant-guess failure class Fable already flagged for topic-KG selection).
3. **`lastUsed` already exists and is written on every single use** (`config.ts:48`, `:204`) — the exact field the design above (§ Registry lifecycle) says the registry "must never grow." The append-mostly/no-current-field invariant this ADR relies on to avoid reintroducing the original bug is already violated by the current schema. Unresolved: is `lastUsed` removed, kept-but-ignored, or does its continued presence mean an older/parallel install on the same machine keeps writing a field the new model depends on not existing?

**Live multi-platform test (2026-07-27) — finding 2 confirmed true for one platform, false for another, unknown for the rest.** With 4 real Claude Code sessions and 1 real Codex session open simultaneously across different project folders, each running MCP server process's actual working directory was inspected directly (`ps`/`lsof`):

The design should stay flexible enough to extend to others later, without requiring that flexibility to be proven out today.

**Revised implication:** this is **not** "assume unreliable everywhere" — it's specifically a **Codex** problem, confirmed correct on both Claude Code and Gemini so far. Still needs per-platform verification before an implementation plan is written (don't extrapolate 2-for-3 into "probably fine everywhere"), but the fix likely doesn't need to abandon trusting the process's own cwd universally — it may need a Codex-specific workaround (or an upstream Codex fix) rather than a heavier cross-platform mechanism (client-supplied roots, MCP `_meta`, etc.) applied everywhere. Worth noting: whatever workaround gets designed for Codex's gap may generalize — the same technique could plausibly cover a future platform with the same "doesn't reliably pass workspace root" problem, rather than needing a bespoke fix per platform.

### Codex workaround found and verified (2026-07-27) — `codex/sandbox-state-meta`

Rather than instrumenting code to observe live MCP traffic, the user asked the live Codex session itself how it handles this — Codex researched its own source and answered with specific file/line citations. **Every claim below was independently re-verified against the real `openai/codex` GitHub repo at the exact cited commit (tag `rust-v0.145.0`) before being recorded here** — not taken on the model's word, per this project's own verification-before-conceding standard:

- **Confirmed: Codex does not implement the standard MCP `roots` capability.** `codex-rs/codex-mcp/src/rmcp_client.rs` constructs `ClientCapabilities::default()` and only ever sets `.elicitation`/`.extensions` — `.roots` is never set, so a server's `roots/list` call has nothing to return.
- **Confirmed: a real, working, capability-gated mechanism exists instead — `codex/sandbox-state-meta`.** If an MCP server advertises this experimental capability in its own `initialize` response, Codex will inject the real, live turn's working directory into `_meta` on **every single tool call**, independent of anything the model generates — verified directly in `codex-rs/core/src/mcp_tool_call.rs`'s `augment_mcp_tool_request_meta_with_sandbox_state`, which reads `step_context.turn.cwd` (the actual current turn's cwd, not the process's).
- **Confirmed: the exact field name matches.** `codex-rs/codex-mcp/src/runtime.rs` defines `SandboxState` with `#[serde(rename_all = "camelCase")]`, so the Rust field `sandbox_cwd` serializes over the wire as `sandboxCwd` — exactly as described. It arrives as a `file://` URI (a `PathUri` type), not a bare path string, so it needs URI-decoding on receipt.
- **Caveat, from Codex's own answer, not yet independently re-verified:** this is a Codex-specific, experimental, undocumented-as-stable extension — not a cross-vendor standard. A fallback (e.g., an explicit `workspaceRoot` tool argument, honored when `codex/sandbox-state-meta` isn't present) is still advisable for any client that doesn't support it, including future platforms.

**This resolves the Codex half of the earlier open question.** The mechanism to adopt for Codex specifically: advertise `codex/sandbox-state-meta` as an experimental server capability, read `sandboxCwd` from `_meta` on incoming tool calls when present, and fall back to an explicit param otherwise. Combined with trusting `process.cwd()` directly on Claude Code and Gemini, this covers all 3 in-scope platforms without requiring one heavyweight cross-platform mechanism.

## Round 2 Brainstorm — Item 4 Resolved: Concurrent Writes + Cross-Branch ID Collision (2026-07-27)

Working through the Opus findings above in order, starting with finding 4 (concurrent same-repo writes with no locking).

**Decision: yes, a real safeguard is needed** — not left as "rare enough to ignore," unlike the full-audit-log item that was deliberately YAGNI'd earlier. Two sessions in the same repo writing to the shared registry file at the same moment need an actual "wait your turn" mechanism (locking / atomic write), not just an accepted risk.

**Folded into the same design item, at the user's explicit request:** a related but structurally distinct risk — **two contributors on different branches independently assigning the same next sequential `ENH-NNN`/`issue-N` number.** Checked the KG for prior art before treating this as new: `issue-11` documents a deep investigation into the `ENH-NNN`/`issue-N` dual-taxonomy question and explicitly notes *"User independently recalls a deliberate discussion existed but confirms it is not recoverable from any available source — treated as lost, not resolved."* That's about *why two ID sequences exist*, not this exact race condition — so this may be the same lost institutional memory surfacing from a different angle, or a genuinely distinct, never-documented concern. Could not confirm either way; recorded here rather than assumed.

**Why this matters more than it looks today:** with the KG stored as markdown files in git, this collision is currently caught for free — two branches both creating `ENH-056` surface a real git merge conflict, forcing a human to look before it lands. That safety net is a property of *the storage medium*, not of any design in this project. If the KG's backing store ever changes to something the MCP server writes to directly and continuously — a database, a shared Notion workspace, a shared network folder — that free protection disappears entirely. Two processes could both silently claim the same ID at the same moment, and whichever write lands last silently overwrites the other's entry, with nothing forcing anyone to notice. **This risk scales in severity with exactly the kind of storage-backend flexibility ADR-066 and this project's broader roadmap already point toward** — it should be treated as a real design constraint on any future non-git-mediated storage backend, not a hypothetical.

**Not designed yet — this session recorded the requirement and its severity, not a chosen mechanism.** Candidate directions for a later pass: a compare-and-swap-style atomic claim on the next number (check-then-write as one operation, fail/retry on conflict) generalizes across both the file-locking and cross-branch-ID-collision cases and would work regardless of backing store. Left open, not decided.

## Round 3 — Second Opus Gap Scan + Resolutions (2026-07-27)

Before continuing further down the original 14-item Opus review list, a second Opus scan was requested specifically to check for *new* gaps of the same "two reasonable rules collide" / "no defined trigger" shape — not a re-review of anything already resolved. It found 8 new candidates. Working through them one at a time:

**1. Personal KG doesn't exist yet — resolved.** No auto-create. Tell the user it doesn't exist, ask if they want to create it, then trigger the personal-init command — the same create-vs-select gate philosophy already established for the (now-descoped) topic-KG case, applied here to the personal KG's first-use case instead.

**2. "Path missing" conflating deleted/moved with temporarily unreachable — resolved.** Before ever asking "was it deleted or moved" (per the Round 2 fix to finding 6), check whether the *parent* directory is reachable at all first. An unmounted drive or sleeping network share means the parent is also unreachable — a different situation from a specific folder genuinely being gone, and shouldn't funnel into the same deleted/moved prompt.

**3. Moved-path repair colliding with an already-registered entry — resolved, with real pushback incorporated, not just accepted as proposed:**
- Tell the user the target already exists as its own registered entry.
- Offer a comparison before merging — but the original idea of pointing the user "outside the CLI" to manually read files was flagged as a stopgap, not a real feature: this project already knows how to compute the kind of comparison data that matters (file counts, overlapping names, last-modified dates — the same class of check built earlier this session for index-drift detection). Building a real compare view is the better answer; punting to manual inspection is an accepted-for-now shortcut, not the permanent design.
- **"Merge" is scoped narrowly: registry entries only, not KG content.** A full content-level merge of two independently-numbered KGs would walk straight into the still-unsolved cross-branch ID-collision problem (Round 2, item 4) — two separate `issue-1`/`ENH-1`... sequences colliding on merge. Merging *only* the registry pointer (stop treating them as two separate registered paths, point at one going forward) avoids that; actual file-tree reconciliation stays a manual, human-led step, optionally assisted by the compare view above.
- **Dry-run required before any actual merge, with explicit approval.**
- **Bypass is allowed, but split into two independent axes, not one:** bypass skips *friction* (the dry-run/review step) — it must never skip *safety* (a backup/undo point is written regardless of whether the user bypassed review). Matches this project's own established pattern elsewhere (PR admin-override, `--admin` merges) and its own ADR-063 invariant (never destroy known-good state before a confirmed write) — overriding the review step is not the same request as overriding the safety net, and the design keeps them separate rather than letting one bypass imply the other.

**4. cwd changes mid-conversation — resolved.** Working in repo A, then `cd`-ing to repo B mid-session, then saying "capture that" correctly targets B by cwd-resolution rules — but flag it once, the first time cwd is noticed to have changed since the last call ("heads up, target's now B"), rather than following silently. Consistent with the "no name given → resolve from cwd, no confirmation" default for the common case, while still surfacing the one moment a user might not expect the target to have moved.

**⚠️ REOPENED 2026-07-27 by Fable review, two ways — (1) RESOLVED 2026-07-28, folded into item 1; (2) still open, see § Fable Review Findings item 5.** (1) "Flag it once" was ambiguous, but the bigger correction: **the "cd to a different top-level registered project mid-conversation" scenario this item was built around doesn't actually happen for Claude Code or Gemini.** The MCP server's cwd is fixed once at process spawn — nothing that happens inside a conversation afterward (including a `cd` run via the Bash tool) changes it, because the Bash tool runs in a separate process from the long-lived MCP server. To work in a different top-level project, a user opens a *new* session there (the 4-separate-processes pattern already confirmed empirically), not a `cd` inside an existing one. What *does* still happen within one session is moving between **nested KGs** (item 1) — e.g. `cd packages/api` inside an already-open monorepo — and that's where this item's flag now lives: fold into item 1's resolution, flagging when the *resolved KG* changes between nesting levels, not on every raw cwd move. (Codex remains a partial exception, per its `sandbox-state-meta` mechanism reading the live turn's cwd — a genuine per-turn location change may be possible there depending on Codex's own turn-context semantics.) (2) The precedence question against item 8 ("stay in personal" vs. a cwd change) is still open — see § Fable Review Findings item 5.

**5. Archived-entry ask-frequency — resolved.** Not a fixed policy (always-ask vs. once-per-session) — an explicit choice offered to the user at the prompt itself, with two distinctly labeled options so they aren't assumed interchangeable: **"Skip"** (just this one time — keep asking again on the next call) vs. **"Ignore"** (stop reminding for the rest of this session). "Always surface, never silent" (Round 2) still holds — this only decides how long an acknowledgment lasts once given, never removes the initial surfacing.

**6. `$HOME`/`/` as cwd — resolved, two-layer.** (a) **Identity check first:** confirm the session's actual OS user matches who owns that home directory — mismatch means warn or stop, not proceed, tying into the security gap the first Opus review flagged (finding 12). (b) **If it is genuinely the user's own home dir:** since Claude Code/Codex/Gemini sessions are normally opened from inside a project folder, a session actually sitting at `$HOME` is unusual enough to be a deliberate signal — so ask plainly, matching the format used throughout: *"You're currently in your own home directory — is this for your personal graph, or one of your existing registered projects?"* Never silently default to personal just because home is a path-ancestor of the personal KG's storage location.

**⚠️ REOPENED 2026-07-27 by Fable review — layer (a) breaks on CI/shared machines.** On a build server or container where everything runs as one system user (`root`, `runner`, `ci`), every session trivially "owns" `$HOME` — the identity check produces zero signal in exactly the automated context most likely to have unrelated jobs colliding. Fable recommends scoping the identity check to interactive/human sessions only, and requiring an explicit `scope` param (no inference at all) for anything automated. See § Fable Review Findings below.

**7. Registered path exists, KG content folder missing — resolved.** Never silent, always ask — but investigate before asking, the same philosophy as finding 2 above (check parent reachability before assuming deleted/moved): if this is a git repo, check other branches/git history first to see whether the content previously existed, was moved, or renamed within git, before presenting the user with a bare "it's missing, want me to recreate it?" prompt.

**8. Ephemeral personal-scope preference — scope and expiry, resolved.** Applies to **both reads and writes** — write-only scoping would leave "what did I note about X?" silently searching the project graph, exactly the "shouldn't have to think about which graph is active" burden this design exists to remove.

**⚠️ REOPENED 2026-07-27 by Fable review — no precedence rule against item 4 above.** If a user says "stay in personal" then `cd`s to a different repo mid-session, this item and item 4 (cwd-change flag) were resolved independently and never cross-checked: does the cwd-change flag silently override "stay," or does personal persist regardless of cwd? See § Fable Review Findings below — not yet decided.

Rather than guessing at auto-clear triggers, **the intent is asked up front, explicitly, the first time personal scope is invoked**: *"Is this a one-shot to your personal graph, or do you want me to keep working there until you tell me otherwise? If you don't say to leave, I'll stay."* This makes indefinite persistence within a session an informed, explicit choice rather than a silent default nobody remembers opting into — and eliminates the need for any auto-clear heuristic (cwd change, call count, etc.) entirely, since the user was told plainly what "stay" means when they chose it. An optional companion shortcut: a prefix at the start of a message/series of prompts — candidates so far: `[personal]`, `[mine]`, `mygraph` — for a fast one-shot without repeating the up-front question every time, analogous to how a status line shows current repo context at a glance in Claude Code/Codex/Gemini today. **Exact keyword not decided, and neither is the marker syntax** — brackets (`[personal]`), a bare word (`mygraph`, `personal`), or some other marker convention entirely (e.g. a leading symbol, a slash-command-style prefix) are all still open; brackets in the examples above are illustrative, not a settled requirement. Same treatment as ENH-055's still-undecided trigger vocabulary.

**Known residual risk, per Opus:** if the conversation is compacted/summarized mid-session, this ephemeral, never-on-disk preference could quietly drop without anyone noticing, silently reverting writes to project-local. Echoing the resolved target on every write (already established elsewhere in this design) makes that visible after the fact, but doesn't prevent it — flagged, not solved, here.

## Live Split-Brain Caught Mid-Session (2026-07-27) — direct, reproducible evidence for the config-file-reconciliation open question

While trying to use `kg_search` (this project's own recall tool) to find the origin of the `githubUser` field discussion, the tool reported its active KG as `docs-readme-poc` — seconds after `~/.kmgraph/kg-config.json` had been read directly and confirmed `knowledge-graph`. Investigated immediately rather than proceeding on a result that might have come from the wrong graph:

- `~/.kmgraph/kg-config.json` (the current, intended-to-be-authoritative location): `active: knowledge-graph`
- `~/.claude/kg-config.json` (the legacy location, which this project's own migration work believed retired): `active: docs-readme-poc`
- The **legacy** file's mtime (Jul 25 15:13) is *newer* than the current file's mtime (Jul 25 11:17) — something is still actively writing to the legacy path, and **the MCP server itself (`kg_search`) reads the stale legacy file, not the current one.**

This is not a new class of problem — it's the exact failure mode this entire ADR exists to close, caught live, first-hand, mid-session, while working on the very design meant to prevent it. It also directly answers one of this ADR's own standing open items ("whether/how the two live divergent config files get reconciled or retired under the new model") with concrete, reproducible evidence: they are **not** reconciled today, one is actively stale-but-still-written, and at least one real code path (`kg_search`) still prefers the wrong one. Any implementation of this ADR's design must include retiring the legacy `~/.claude/kg-config.json` path outright, not just adding new resolution logic alongside an unreconciled duplicate.

### C. New use cases, not previously considered by this document or either Opus pass

8. **CI/headless/non-interactive callers.** The entire design leans on "ask the user" repeatedly (fuzzy match, archived entry, first-time-repo write, nested-KG conflict, `$HOME` check) — nothing addresses a scripted/CI caller with no user to answer a blocking prompt. **Recommendation:** a distinct non-interactive mode (explicit `confirm: true`/`--yes` param, or a pre-registered CI allowlist) that fails closed with a machine-readable error instead of hanging, for every branch that would otherwise ask.
    **Opus: AGREE, strongly — best of the six new use cases.** Prefer the explicit `confirm`/`--yes` param over a CI allowlist — an allowlist is new shared mutable state, i.e. this ADR's own bug class one layer down. Pair with item 3's interactive/automated discriminator so there's one non-interactive determination, not two separate ones.
9. **Long-running sessions caching a stale resolution.** If a session/process stays open for hours or days and caches a resolved KG path, another session archiving or renaming that entry mid-session leaves the long-running one silently acting on stale registry state — a narrower reintroduction of the exact bug this ADR exists to close. **Recommendation:** always re-read the registry from disk on every call; never cache a resolved target across calls within a process lifetime (the registry file is small — this is cheap).
    **Opus: PARTIAL — the recommendation is already the implementation, verified.** `readConfig()` has no caching anywhere (17 call sites, all fresh `fs.readFileSync`, `utils.ts:51`) — record this as a regression guard, not a fix. **The real long-running-process hazard is different and wasn't caught by Fable**: all 5 live MCP server processes on this machine right now are running **stale plugin-cache code** (v0.6.16, two of them 2+ days old) — a more plausible explanation for the earlier live split-brain incident (§ Live Split-Brain Caught Mid-Session) than stale config data. Recommend a post-upgrade staleness signal (detect and warn when a running server process's code version is behind the installed plugin version), not a no-cache rule that already holds.
10. **Subagents don't inherit the ephemeral personal-scope preference.** § Round 3 item 10 resolved that this preference lives in server-process memory, safe because each session is its own process — but a subagent spawned by a top-level session is very plausibly a *different* process, so the preference silently won't apply to it. **Recommendation:** explicitly document that scope preference is top-level-session-scoped by design and does not propagate to subagents; any orchestrator wanting personal-scope behavior in a subagent must restate `scope: "user"` explicitly per call.
    **Opus: DISAGREE with the premise — likely backwards, needs verification before documenting either way.** Claude Code subagents may *share* the parent session's MCP server connection rather than spawning their own — the process-count check earlier in this document (§ Live multi-platform test) matched *session* count, not sessions-plus-subagents, so this was never actually tested. If subagents share the connection, the risk inverts: the preference **would** silently propagate, granting personal scope to a subagent whose scope the orchestrator never confirmed — the opposite of what's stated here. The "restate `scope` explicitly per call" rule is right regardless of which way this goes, so adopt it — but do not document "does not propagate to subagents" until the actual process model is verified per platform, the same way cwd behavior was.
11. **Session resume after a real process restart (not just mid-session compaction).** Item 8's residual-risk note (§ Round 3) covers compaction; it doesn't cover closing and reopening a session (laptop sleep, "continue previous conversation"), which respawns a fresh process and silently drops "stay in personal" even though the transcript still shows the user asked for it. **Recommendation:** on session resume, if transcript history shows an active, unrevoked "stay" preference, proactively re-confirm scope at the first `kg_*` call of the resumed session.
    **Opus: AGREE the gap is real, and empirically supported** (the same stale 2-day-old processes found in item 9 confirm resume-without-restart is a live scenario on this machine). **DISAGREE with the mechanism** — reading transcript history to detect an "unrevoked stay" is fragile, platform-specific, and reintroduces state-reconstruction logic. Simpler and safer: treat resume identically to a cold session start — no preference carried over at all, and the first personal-scope call just re-asks item 8's up-front question. Fails safe to project-local by default, which is the correct failure direction.
12. **Accidental duplicate registration of the same physical KG.** A repo cloned to two different paths and `kmg-init`'d twice (common for contractors keeping a "clean" and "working" copy, or CI checkout dirs, or re-cloning a client repo to a new location mid-engagement) produces two independently-numbered registry entries for what's conceptually one KG — hitting the cross-branch ID-collision problem (§ Round 2, item 4) from a trigger this document never named. **Recommendation:** at `kmg-init`, check for a lightweight KG-identity marker already present in another registered entry (not just a path match) and warn "this looks like the same graph already registered at X — reattach here instead?" before creating a second independent registration.
    **Opus: AGREE, and verified there is no identity marker of any kind today** (no `uuid`/`graphId`/equivalent anywhere in `mcp-server/src`). **Improve the recommendation's placement:** put the marker in the KG's own content directory (a `graphId` in the KG's own metadata), not in the registry entry. That way it travels with clones, moves, and re-checkouts automatically — and it also resolves § Round 3 item 3's moved-path-vs-existing-entry identity question for free, and gives the compare-view mentioned there a real join key. One construct, three open problems closed.
13. **No way to browse activity across many registered KGs.** A team lead on a shared machine with dozens of registered project KGs across rotating contributors has no way to ask "what did the last few people log" — the model optimizes single-user ergonomics but has no bulk/cross-registry read path, and none of `.active`/MRU exist to lean on anymore by design. **Recommendation:** a dedicated, strictly **read-only** "list recent activity across all registered graphs" tool, sorted by each entry's own `lastUsed`/timestamp (once item 4 above is resolved) — scoped to reads only so it can't reintroduce write-target ambiguity.
    **Opus: PARTIAL.** Read-only scoping is right, but the proposed sort key is broken — `lastUsed` has no recurring writer today and none after item 4's resolution (remove it), so sort by newest content-file mtime per graph instead. **Bigger unaddressed issue Fable didn't raise:** a "what did the last few contributors log" tool on a shared machine is inherently a cross-contributor read across every registered graph — directly in tension with the contractor-isolation rationale that drove Opus's original item 9 (never fall back to personal, keep customer content strictly separate). This needs its own explicit consent/scoping story before it's designed, not just a read-only guarantee.
