## Context

Raised 2026-07-15 while reviewing the issue-14 config-path fix. This is a **future architectural question**, captured so it is not lost. It is **not** part of issue-14 and does not gate c1/c2/c3.

### The current model

KMGraph resolves "which knowledge graph am I operating on" through a **single mutable pointer**: `kg-config.json` holds an `.active` field, `/kmgraph:kmg-switch` rewrites it, and every tool/command reads `.active` to pick the target KG. This is **global mutable state** — one active KG at a time, shared across all sessions and all projects on the machine.

### Why this is being questioned (the bleed risk)

A single mutable `.active` pointer has structural failure modes where a correct path string still routes an operation to the wrong KG:

1. **Stale/divergent pointer** — the exact split-brain issue-14 is fixing: `.active` written to one config file, read from another. More generally, any staleness in `.active` sends a write meant for KG-A into KG-B.
2. **Concurrency** — two Claude Code sessions (or two projects) open at once share one `.active`. Switching in session 1 silently changes the target for session 2 → cross-KG contamination ("bleed").
3. **Context mismatch** — the active KG can disagree with the current working directory / project. (Prior art: issue-10 added a `getProjectRoot()` / `KG_MISMATCH` guard that *detects* active≠cwd, i.e. the project already treats this mismatch as a hazard worth guarding.)

### The alternative under consideration

Instead of a mutable toggle, resolve the KG from **context** — derive it from the project root / working directory (and/or an explicit per-invocation argument), the way the context-mode plugin centralizes context resolution. This would make "which KG" a function of *where you are*, not a stateful global flag, structurally eliminating failure modes 1-3.

### Interaction with in-flight work

- c1 (issue-14) fixes `kmg-switch`'s config path **now**; that fix is correct regardless of this decision (the switch still writes to the right file in the interim).
- If a future decision **replaces** the mutable-switch model, the `kmg-switch` command (and its c1 fix) would be **superseded**, and the resolution logic across every `kg_*` tool and command would change. This is a large blast radius — hence a dedicated ADR, not a patch.

## Prior Art (recall + chat-history sweep, 2026-07-15)

A recall + `knowledge/chat-history/2026-02/` sweep was run before framing this decision. Findings:

- **Separation itself was never a reasoned decision — it is an unexamined premise.** `ADR-001:16` ("designed to support multiple independent knowledge graphs, each potentially owned by different users or projects") and `ADR-001:28` assume separation; no ADR argues isolation/privacy/anti-bleed as the reason to keep graphs separate. Ironically [[ADR-001-centralized-multi-kg-configuration]]'s stated *problem* was the opposite — **fragmentation** (too separate, no coordination), not bleed. Any isolation rationale this ADR needs must be **authored**, not quoted.
- **The `.active` + switch model was deliberate — but weighed only against config-file alternatives, not against context-derived resolution.** `ADR-001:85-95` (Alternatives Considered):
  - **Option A — per-project `.claude/kg-local.json` (self-contained, the closest proxy to cwd/context-derived):** *rejected* — "Can't switch between KGs; must edit per-project config to use global KG." I.e. it could not serve "different KGs for different tasks" or reach a global/cowork KG from inside any project directory.
  - **Option B — env var `KG_PATH`:** rejected (fragile, no discovery).
  - Positive rationale (`ADR-001:80-83`): single source of truth; **git-like active-pointer pattern**; extensible; backward-compatible.
- **Pure context/cwd-derived resolution was never proposed before this ADR (2026-07-15).** [[ADR-001-centralized-multi-kg-configuration]] foreclosed it structurally without naming it.
- **`ADR-060` already characterized the switch as intentionally manual, contrasting context-mode.** `ADR-060:35` was "Prompted by a user question ('recall why we switch KGs manually and context-mode doesn't')"; `ADR-060:29,59` frame [[ADR-001-centralized-multi-kg-configuration]]'s model as **"manual/git-like, not auto-detected like context-mode's project scoping"** — serving intentional, durable knowledge management. This is the strongest "it was intentional" citation (though [[ADR-060-narrow-kg-search-scope-away-from-raw-chat-history]] interprets [[ADR-001-centralized-multi-kg-configuration]]'s intent after the fact; [[ADR-001-centralized-multi-kg-configuration]] never wrote "we rejected auto-detection").
- **The Option-A rejection reason is still live** — a cwd-bound model has no home for the personal/global/cowork cross-project KGs that are intentionally *not* tied to a directory. This is precisely open question [#2](https://github.com/technomensch/knowledge-graph/issues/2) below, and it pushes the answer toward a **hybrid** (context-derived default + explicit override) rather than a clean replacement of the switch.
- **Bleed has a concrete track record that favors revisiting:** `ADR-019` (v0.2.0-beta) first named the wrong-graph-write hazard and added an agent-instruction write guard; the data-layer `KG_MISMATCH` guard (`kg_capture`, issue-10) was meant to harden it but shipped as a **false-positive bug** ("currently more friction than protection", `issue-10-description.md:31`); and issue-14 is the live split-brain. The mutable-pointer model has now produced **two distinct real bugs** where correct-looking state still routed to the wrong KG — direct evidence for the failure modes in the Context above.

## New Incident + a Working Mitigation, Observed Live (2026-07-21)

A third real drift incident, on the `v0.6.20-storage-migration-completion` branch: `.active` was confirmed correctly pointing at `knowledge-graph` earlier in the same session (checked directly before running `kg_upgrade` operations), then found — later in the same session, no `kmg-switch` call in between — pointing at `docs-readme-poc`, a completely unrelated project. Root cause not investigated (out of scope for the in-flight branch); the point is the drift happened silently, mid-session, exactly as failure mode 2/3 above predict, with no action taken by the user or the assistant to cause it.

**What explicitly did NOT go wrong, and why — this is the useful part.** Two background agents were writing real content to `knowledge-graph`'s own `knowledge/sessions/` and `handoff-packages/` during this exact drift window. Neither wrote to the wrong project. Both were given an **explicit absolute working directory** and **explicit relative file paths** in their task prompts, and used direct file Read/Write/Edit tools — never a `kg_*` MCP tool, which is the only thing that actually resolves against `.active`. The active-pointer's value was simply never consulted for these writes; the operation was anchored to an explicit path from the start, not resolved from ambient state.

**This is a concrete, observed data point for the open decision, not just a hazard restated:** explicit-path / context-anchored operations are *structurally immune* to `.active` drift, by construction — not because they're careful, but because they never ask the question `.active` answers. This is direct empirical support for the "context-derived resolution" side of question 1 below, and independently, a viable *interim* mitigation while the ADR stays undecided: prefer giving agents/tools an explicit target path over relying on implicit active-KG resolution, whenever the target project is already known. Worth weighing explicitly when this is picked up — not as the final answer (it doesn't address the cross-project personal/global KGs that have no cwd, per question 2), but as evidence of which failure modes an explicit-path convention already closes today, without waiting on this decision.

## Decision

**PENDING — not yet decided, and deliberately deferred beyond the current session.** Questions to resolve when this is picked up:

1. **Do we keep the mutable `.active` switch, or move to context-derived resolution** (project-root/cwd-based), or a hybrid (context-derived default + explicit override)?
2. If context-derived: **how is the KG chosen when cwd maps to no registered KG**, or to more than one? What replaces the "personal / global / cowork" cross-project KGs that are intentionally *not* tied to a cwd?
3. **Concurrency semantics** — is "active KG" per-machine, per-session, or per-project? (The bleed risk is fundamentally about this scope.)
4. **Migration path** — how do existing installs relying on `.active` + `kmg-switch` transition without breaking? What happens to the `kmg-switch` command and its issue-14/c1 fix?
5. **Relationship to issue-10's `KG_MISMATCH` guard** — does context-derived resolution subsume it, or coexist?

_No option selected. Consequences, migration design, and cascade impact across all `kg_*` tools, commands, and the switch surface are deferred until the decision above is made._

## Brainstorm Session Findings (2026-07-21) — spec-in-progress, decision still PENDING

A `/superpowers:brainstorming` session on this ADR produced the following. **This is design-in-progress captured for continuity, not a decision** — status remains Proposed/pending.

### User's stated bottom line (verbatim intent)

"Having one authoritative graph that is constantly switching is not going to work. Users work on multiple projects simultaneously and should not have to think about which graph is active. If a user is in one repo/folder in one terminal session, the graph should know to write/read from that one. If there is a parallel session working in a completely different repo, the user should read/write from that one without having to think about it. There should be no bleed between them. The only overlap might be both being able to read the user-level graph which goes across all local projects. Each session might even be in different LLMs — one in Claude, another in Codex, in a different repo."

This resolves Q1's direction: **no mutable `.active` switch** as the default resolution mechanism. Replace with **stateless, context-derived (cwd/project-root) resolution per call** — no shared file is read as "current truth," so concurrent sessions (even across different LLM tools) cannot bleed into each other by construction, because there is nothing shared to drift.

### Emerging Q1 model (not yet finalized)

- **Project-local KG**: auto-resolved from cwd/project-root at call time, no switch needed. Candidate mechanism: promote issue-10's existing `getProjectRoot()` from a mismatch *guard* to the actual *router*.
- **Personal KG** (singular, cross-project): always reachable regardless of cwd, addressed via an explicit param on the call (not a global switch) — e.g. `scope: "user"` — rather than a stateful toggle.
- **Agent-level judgment on when to search which scope** (e.g., search project by default, offer "want me to check your personal KG too?" as a follow-up rather than hard-coding a merged-search default) is explicitly **out of scope for this ADR** — flagged as a question for the fable/planning pass, not an architectural rule.

### Research findings that complicate/refine the model (agent sweep of chat-history + KG + live config, 2026-07-21)

1. **Historical switch usage was project↔project only, never project→personal.** All 18 real `kmg-switch` invocations found in `knowledge/chat-history/` (2025-12 through 2026-07) swap between project-local KGs (e.g. `knowledge-graph` ↔ `docs-readme-poc`). No instance of switching to a personal KG exists — because none has ever been created on this machine, despite [[ENH-001]] "completing" the code path in 2026-03. This *strengthens* the case for killing the switch: the actual historical pain (project↔project switching) is exactly what cwd-derived resolution eliminates.
2. **A live split-brain instance exists right now, in this repo, at the moment of writing.** `~/.kmgraph/kg-config.json` currently reads `active: docs-readme-poc` while cwd is `knowledge-graph`. A second, stale legacy copy at `~/.claude/kg-config.json` reads `active: knowledge-graph`, frozen mid-migration since 2026-07-17 (`lastAppliedVersion: 0.3.10`). This is the exact drift class this ADR already documents (the 2026-07-21 incident, above), caught live rather than reconstructed after the fact.
3. **Only 2 KGs are registered today, both `project-local`** (`knowledge-graph`, `docs-readme-poc`). No `personal` or `global-topic` KG exists yet on this machine.
4. **The real taxonomy is three shapes, not two.** [[ADR-066-kg-content-storage-location-for-global-and-cowork-modes]] (resolved 2026-07-17, not yet implemented as of the v0.6.20 plan) kills `cowork` as a KG type but keeps **global-topic KGs** as a separate first-class concept: arbitrary count, user-named, stored at `~/.kmgraph/knowledge-graphs/<name>/`. So the model is **project-local (many, cwd-resolved)** + **personal (exactly one, singular)** + **global-topic (many, named)**. The emerging Q1 model above only accounts for project vs. a single "user-level" scope — it has **no answer yet for selecting among multiple named global-topic KGs**, which is likely Q2 territory (what happens when cwd maps to none/multiple candidates) rather than a Q1 concern, but is flagged here so it isn't lost.
5. **Two live bugs in the current write path that any new resolution model must not silently inherit:**
   - **issue-15**: `capture.ts`'s `rebuildIndex()` never passes `kgType`, so writes targeting a `personal` KG get indexed under the `project-local` FTS5 bucket.
   - **issue-27**: `applyStrayKnowledgeDir()` silently overwrote real KG content by skipping a destination-exists check — reinforces that any new resolution logic needs an explicit "never silently overwrite/misroute" invariant ([[ADR-063-never-destroy-known-good-state-before-confirmed-write]] pattern).

### Fable Review (2026-07-21) — independent second opinion, requested mid-brainstorm

Fable (`claude-fable-5`) was given the emerging model above plus the research findings and asked for (a) a recommendation on global-topic KG selection and (b) any gaps in the model not already surfaced. Response:

**Recommendation — registry lookup + mandatory disambiguation, not keyword-match or MRU.** Require an explicit `topic` param on every call, resolved via a registry/manifest lookup (list of topic-KG names + short descriptions) *before* the call: the tool exposes a lightweight list/lookup, the assistant performs one resolution pass (exact name match, or fuzzy match against name/description), and only passes the param once confident. If zero or multiple candidates match, the tool refuses and forces the assistant to ask the user rather than guess.

*Alternatives considered and rejected, per Fable:*
- **Keyword/topic matching as the sole mechanism** — risks exactly the failure class being eliminated: silent misdirection, just non-deterministic instead of stale-pointer.
- **Most-recently-used heuristic** — definitionally the same bug pattern as `.active` in a different hat: implicit shared state that drifts.
- **Pure "always ask the user"** — safe, but degrades UX for the common case where the assistant can resolve unambiguously (e.g., user said "log this under woodworking" and only one KG matches).
- The registry approach gets assistant-side confidence *and* keeps writes deterministic and explicit. Reads can be more permissive (fan-out across matches is low-risk); writes cannot.

*Stated failure mode of its own recommendation*: depends on the assistant actually performing the lookup step every time. Under time/context pressure an assistant can skip the list-and-match round trip and pass a remembered or hallucinated topic name directly. If that name doesn't exist, the result is a clean error (safe). If it's a near-miss of an existing name (typo, pluralization, stale name after a rename), the result is a misdirected write that looks superficially fine — the same class of silent-wrong-target bug, just moved from "shared mutable pointer" to "assistant's guess," and harder to detect because there's no drift signal to notice. Mitigation: the tool should always echo back the resolved KG name/description in its response, so misdirection is at least visible to whoever reads the result, even if not structurally prevented.

**New gaps identified (beyond what this ADR had already surfaced):**

1. Read/write need explicitly different resolution defaults (fan-out-merge for search, never for capture), not one shared algorithm with variable strictness.
2. The registry itself is new shared mutable state, same failure class as `.active`, just narrower scope — must stay append-mostly and never grow a "current"/"last used" field, or the bug reappears one layer down.
3. First mention of a brand-new topic name is a *creation* decision, not a *selection* one, and needs its own gate.
4. Namespace collisions are unhandled: nothing stops a topic-KG name from colliding with a project directory name or the reserved "personal" scope.
5. The known indexer bug (issue-15, missing `kgType`) is a symptom of implicit/positional scope-tagging generally, not a one-off — the fix needs to make type an explicit required tag at write time everywhere, or the same bug recurs for topic KGs.
6. No lifecycle story exists for delete/rename of a topic KG while another session holds a reference to it by name — structurally the same live-reference problem as the concurrent-session bleed being fixed for project-local KGs, but unaddressed for the registry case.

## Cross-Tool Comparison: gh's per-repo identity switching (2026-07-25)

While debugging an unrelated problem in a different session/repo (`docs-readme-poc`) — `gh auth switch` not giving true per-terminal isolation because `gh` reads one shared `~/.config/gh/hosts.yml` regardless of terminal — the user was given this fix by that session's assistant, and asked whether it's applicable to ADR-067. Captured here as a validating data point, not a decision.

**The gh fix, two parts:**
1. `GH_CONFIG_DIR` env var override, pointed at an isolated per-identity config dir (`~/.config/gh-tidal`), set manually per terminal (or via `direnv`/`.envrc`).
2. Optional zsh `chpwd` hook in `~/.zshrc` that auto-sets/unsets `GH_CONFIG_DIR` on `cd` into a specific repo — recomputed fresh every directory change, nothing persisted as "current identity" between calls.

**Assessment: validates the principle, mechanism doesn't transfer directly.**

- Part 2 (chpwd hook) is structurally the same pattern as this ADR's context-derived direction: derive the answer from cwd at the moment of the call, instead of storing it in a mutable pointer that can drift (`.active` / `GH_CONFIG_DIR`-if-forgotten-to-unset). Real independent evidence for "derive, don't store."
- The mechanism doesn't reuse as-is because gh is a plain CLI — each invocation is a fresh process with no way to know "where am I" except reading ambient shell state, so a shell hook is the only lever available. KMGraph's `kg_*` tools are MCP tool calls that already run inside code with direct access to cwd/project-root at call time (`getProjectRoot()`, `mcp-server/src/utils.ts:106`, already wired as a mismatch guard in `capture.ts:254`, per issue-10). Introducing a shell-level env var here would add a new class of persisted state (shell-session-scoped) — the same failure category as `.active`, just relocated, not eliminated.
- Where the two do line up structurally: isolated storage-per-identity (`~/.config/gh-tidal`) mirrors isolated storage-per-project-KG (`~/.kmgraph/knowledge-graphs/<name>/`, per [[ADR-066-kg-content-storage-location-for-global-and-cowork-modes]]) — a storage-layout parallel, not a resolution-logic one.
- Confirms the actual feasibility test for this ADR is promoting `getProjectRoot()` from guard to router inside `kg_*` handlers directly (code already half-built via issue-10), not a shell-hook analog.

Real-world test in progress: user is attempting to get the gh `chpwd`-hook fix itself working, live, in the `docs-readme-poc` session/repo — a separate, unrelated debugging effort, not part of this ADR's implementation.

## External Research (2026-07-26) — industry precedent, still no decision

A web search for prior art on this exact class of problem (global mutable "current selection" state vs. deriving the answer from context per-call), requested explicitly to sanity-check the direction against outside evidence rather than only this project's own history.

**1. `kubectl`'s `current-context` has the identical, well-documented bleed failure.** Multiple independent sources describe the same symptom this ADR names: a second terminal silently picks up a context change made in a first terminal, because `kubectl` reads one shared `~/.kube/config` `current-context` field regardless of which terminal or directory issued the change — structurally the same bug class as `.active`, just a different tool. The ecosystem's actual fix in practice is **not** a better switch command (`kubectx` itself is called out as still carrying the same global-mutation risk) — it's abandoning the shared pointer for either (a) `KUBECONFIG` env-var scoping per project, or (b) `direnv`, which loads/unloads directory-scoped state on `cd` with "variables never leak" as the explicit design goal. This is real-world confirmation that the "derive from context, don't store a shared pointer" direction already adopted above is the field's actual converged answer to this exact failure mode, not a novel or risky choice.

**2. The MCP protocol itself is moving to statelessness in days, not years.** The 2026-07-28 MCP specification release candidate (SEP-2567, SEP-2575) removes the `initialize` handshake and the `Mcp-Session-Id` header entirely — every request now carries its own context in `_meta`, with no persisted session state and no sticky-routing requirement, specifically because "the Model Context Protocol's session-based architecture has been a production liability." KMGraph's `kg_*` tools are MCP tool calls running on this exact protocol. This lands directly on Q1: promoting `getProjectRoot()` from a mismatch guard (issue-10) to the primary per-call router isn't just internally consistent with this project's own evidence — it's the same architectural direction the protocol layer underneath it is independently taking, for the same underlying reason (a shared session/pointer is a liability; a self-describing per-call request is not).

**3. Multi-tenant MCP isolation guidance converges on explicit-scope-per-call, never inferred from shared state** — consistent with, not a new input to, the registry-lookup + mandatory-disambiguation direction already adopted above for personal/global-topic KG selection.

**Assessed scope of findings 1+2 — validates one half of the model, does not replace the other half.** Both findings are strong, independent confirmation for the **project-local** resolution case (cwd-derived, stateless, per-call) — which is also the empirically dominant case (all 18 historical `kmg-switch` invocations were project↔project). Neither finding has an analog for **personal KG** (singular, no cwd to derive from) or **global-topic KGs** (multiple named candidates; cwd carries no signal about which one is meant). `direnv`/`KUBECONFIG` scoping and the MCP stateless spec both solve "know where you are," not "pick one of several named things with no locational signal" — so they cannot substitute for the registry-lookup + mandatory-disambiguation mechanism (Fable's recommendation, § Brainstorm Session Findings above) for that second case. Adopting only findings 1+2 and dropping the registry-lookup piece would silently leave personal/global-topic KGs unresolved — the same shape of gap Option A was rejected for in [[ADR-001-centralized-multi-kg-configuration]]'s original alternatives analysis. **Conclusion: findings 1+2 confirm and strengthen the project-local half of the emerging model; they do not replace the explicit-param/registry-lookup half, which stays in the model.**

### Scope correction: two KG shapes, not three

Global-topic KGs ([[ADR-066-kg-content-storage-location-for-global-and-cowork-modes]]'s third taxonomy shape) are **out of scope for this decision**. The project is designed around per-project and per-person graphs today; no real "topic spanning multiple projects" use case has been observed. Captured separately as **[[ENH-053]]** rather than designed for speculatively. This simplifies the model to exactly two shapes:

- **Project-local** (many) — resolved from cwd/project-root, per call.
- **Personal** (exactly one) — the thing "my graph"/"user graph"/"personal"/"personal graph" all refer to, interchangeably; lives outside all repos in `~/.kmgraph/`. Resolved via an explicit `scope` param, not a switch.

### Resolution flow (resolves Q1 and the registry-lookup question)

1. **No name given** → resolve from cwd/project-root, without asking *which graph* — no disambiguation question. This is the default path and the empirically dominant case (all 18 historical `kmg-switch` invocations were project↔project). This does not mean total silence: a one-line notice can still fire in specific cases — item 12(a) (§ Opus Review Findings) on a first-time-seeing-this-repo write, and item 1's nested-KG-transition flag (§ Fable Review Findings item 1) when the resolved KG changes between nesting levels. **(Wording fixed 2026-07-28, § Fable Review Findings item 6 — the original "silently, no confirmation" phrasing was ambiguous, not wrong; only the disambiguation-question was ever meant to be skipped.)**
2. **Name given, exact match against the existing `graphs` registry** (in `kg-config.json` — no new registry construct needed) → route directly.
3. **Name given, fuzzy match(es)** (typo, pluralization, stale rename) → **always** show the candidates and ask which one is meant — no silent fan-out, for reads or writes. (Resolves the read/write-asymmetry open question: there is no asymmetry. Concrete motivating example from the user: `docs-readme-poc` vs. `docs-mintlify-poc` — two real, unrelated POCs on this machine that share a fuzzy prefix; blending their results on a read would be worse than asking once.)
4. **Name given, no match at all** → tell the user it isn't registered. **No search of unregistered locations** — KMGraph only knows about projects that have run `kmg-init` and registered; searching for an arbitrarily-named, arbitrarily-located, arbitrary-VCS folder it has never seen before is unreliable by construction (not all projects live under one folder, not all use git, naming is arbitrary) and was explicitly rejected as a design direction rather than merely left undesigned. (This is distinct from the ordinary, bounded filesystem access step 1 already requires — walking upward from cwd to find which *already-registered* project root it falls under. That's matching against known data, not searching for unknown folders.) If the user means a real project, the answer is "go there and run `kmg-init`," not an automated search.

### Registry lifecycle (resolves the archive/delete open question)

- Existing `graphs` entries gain a lightweight lifecycle: **`status`** (`pending` / `active` / `archived` / `deleted`) + **`statusChangedAt`** timestamp + optional **`githubUser`** (if applicable) — added to the entry, not a new field on top of it. (`pending` added 2026-07-28, § Fable Review Findings item 7 — initial status at registration, flips to `active` on first confirmed write; resolves the first-time-seeing-this-repo persistence gap with no new schema.)
- **Archive, don't hard-delete.** Archiving flips status + timestamp only; the KG's actual content directory is never touched ([[ADR-063-never-destroy-known-good-state-before-confirmed-write]] invariant — never destroy known-good state before a confirmed write).
- **Writing to an archived/deleted entry never happens silently** — surface "this graph was archived on `<date>`," offer to restore, before proceeding.
- A **full history log** (every transition, not just current status) was explicitly considered and deferred — YAGNI'd out, captured as **[[ENH-054]]** — because nothing discussed needs "how many times has this been archived," only "is it archived, since when, offer to undo."
- This satisfies Fable's earlier-flagged gap (§ Brainstorm Session Findings above, gap [#2](https://github.com/technomensch/knowledge-graph/issues/2): "the registry itself is new shared mutable state... must stay append-mostly and never grow a 'current'/'last used' field") — `status`/`statusChangedAt` is a per-entry state field, not a shared "current" pointer, so it doesn't reintroduce the bug this ADR exists to close.

### `kmg-switch` and the `KG_MISMATCH` guard — both retired

- **`kmg-switch` is retired as a config-mutating command in any form**, including a version scoped narrowly to just the personal-graph case. Any disk-persisted "current target" — even small — reintroduces the exact drift risk this ADR exists to close, just with a smaller blast radius. Personal-graph access becomes an explicit `scope` param per call; the "I want to talk to my personal graph for a while without repeating the param" ergonomic need is met by an **ephemeral, in-session-only preference — never written to disk, never shared across sessions**.
- **issue-10's `KG_MISMATCH` guard becomes dead code once this model is live** — there's no separate "active" value left to disagree with cwd, because cwd *is* the resolution. Confirmed explicitly by the user ("if this new framework works the way it is supposed to, then I guess it would make it redundant"). Retire it as part of migration rather than leave it stranded.

### Inherited constraints (not new decisions — existing bugs the new model must not reproduce)

- **issue-15**: `kgType`/scope must be an explicit required tag at every write call, never inferred positionally — closes the personal-KG-writes-misindexed-under-project-local-FTS5-bucket bug.
- **issue-27**: never silently overwrite/misroute — applies to the archived-entry-write case above as much as it did to `applyStrayKnowledgeDir()`.

### Migration path (resolves the last open question)

- Rides the **existing `upgrade-inspector` mechanism** (same one already shipped for the cowork/global-topic migration in v0.6.20) rather than a bespoke script — proven to actually reach users, unlike a migration that only exists as unreached code (see issue-28's dev-loop gap, which is exactly the failure mode a *disconnected* migration script would hit).
- **Explicit, plain-English notice** of the behavior change, **explicit consent** before cutover, **originals backed up** before any destructive step — matching [[ADR-063-never-destroy-known-good-state-before-confirmed-write]] and the precedent already set by the cowork-mode migration. Discussed and explicitly endorsed as the right level of transparency (with real external precedent: `git`'s multi-year `init.defaultBranch` warning-before-enforcing rollout, Kubernetes's deprecation-window + explicit-conversion-tool pattern for breaking API changes — silent behavior changes on anything that affects *where data goes* are the industry's known anti-pattern, not this project inventing new ceremony).
- Reconciles the two currently-divergent config files (`~/.kmgraph/kg-config.json` vs. legacy `~/.claude/kg-config.json`) as part of the same step.

### Newly captured, explicitly out of scope

- **[[ENH-053]]** — topic-KGs spanning multiple related projects (not user-graph, not single-project). Descoped from this decision; revisit only if a real use case appears.
- **[[ENH-054]]** — full audit-trail history log for registry lifecycle transitions (vs. the lightweight status+timestamp adopted above). YAGNI'd deliberately.
- **[[ENH-055]]** — `kmg-capture-router`'s trigger vocabulary misses "future enhancement"/"worth capturing" phrasing entirely (same failure class as the already-documented "Skill Auto-Triggers Miss Process Vocabulary" lesson) — surfaced live when [[ENH-053]] and [[ENH-054]] didn't auto-capture during this same brainstorm.

### Codex workaround found and verified (2026-07-27) — `codex/sandbox-state-meta`

Rather than instrumenting code to observe live MCP traffic, the user asked the live Codex session itself how it handles this — Codex researched its own source and answered with specific file/line citations. **Every claim below was independently re-verified against the real `openai/codex` GitHub repo at the exact cited commit (tag `rust-v0.145.0`) before being recorded here** — not taken on the model's word, per this project's own verification-before-conceding standard:

## Round 2 Brainstorm — Item 4 Resolved: Concurrent Writes + Cross-Branch ID Collision (2026-07-27)

Working through the Opus findings above in order, starting with finding 4 (concurrent same-repo writes with no locking).

**Decision: yes, a real safeguard is needed** — not left as "rare enough to ignore," unlike the full-audit-log item that was deliberately YAGNI'd earlier. Two sessions in the same repo writing to the shared registry file at the same moment need an actual "wait your turn" mechanism (locking / atomic write), not just an accepted risk.

**Mechanism resolved 2026-07-28, after an Opus sanity-check of an initial draft found the draft conflated two different problems** — atomic rename gives *crash safety* (no torn file), it does not give *mutual exclusion* (no lost updates); a separate mechanism is needed for each.

- **Crash safety:** write to a temp file, `fsync` it, then atomic-rename over the target — never a direct `fs.writeFileSync`. Real-world requirements the naive version misses: the temp file must live in the **same directory** as the target (rename fails across filesystems, `EXDEV` — load-bearing here since `CONFIG_PATH` is env-overridable via `KG_CONFIG_PATH`, so "same directory" isn't a fixed constant); the temp filename must be **unique per process** (pid + counter), or a fixed temp name reintroduces the exact race being closed; and **Windows needs a bounded retry around the rename call itself** — `MoveFileExW` there can transiently fail with `EPERM`/`EBUSY` when antivirus, Search Indexer, or OneDrive briefly holds a handle on the destination, unrelated to any real conflict. File permissions/mode should also be preserved explicitly — a rename replaces the inode, so a user's own `chmod` on the config silently reverts otherwise. (`write-file-atomic`, the pattern npm's own CLI uses, is a solid reference implementation for all of the above, even if not taken as a dependency.)
- **Mutual exclusion — not true compare-and-swap, record it honestly as risk-reduction.** Before the final rename, re-compare the file's raw bytes (already held in memory from the original read — cheaper and more reliable than a timestamp or hash comparison; file mtime has real granularity/staleness failure modes on some filesystems) against a fresh read. If changed, someone else wrote in between. **But retrying isn't actually implementable against this codebase's current API shape as-is** — every one of the 7 write call sites does read → mutate the object in hand → write it back; on a detected conflict there's nothing to redo except write back the same now-stale object, losing the other write anyway, just slightly later. Two ways out, prefer the second: (a) refactor every call site to a `updateConfig(mutatorFn)` shape that re-runs the mutation against a fresh read on conflict — correct, but a real cross-cutting refactor; (b) **merge only the specific registry keys that changed, rather than writing back the whole object** — realistic collisions are disjoint in practice (one session registers graph A while another archives graph B), so a key-level merge resolves the conflict by construction instead of detecting and retrying it. The one genuinely contested field is the scalar `active` pointer, where last-writer-wins is arguably the correct behavior anyway (whichever switch happened most recently is what the user meant). Even with the merge approach, a window remains between the re-check and the rename — smaller (microseconds, not seconds), not zero; this document should say so plainly rather than imply the race is fully closed.
- **Sequencing dependency, not previously stated:** `readConfig()` falls back to the legacy `~/.claude/kg-config.json` path when reading, but `writeConfig()` unconditionally writes only the current `CONFIG_PATH` — the exact split-brain this ADR documents live (§ Live Split-Brain Caught Mid-Session). In that fallback case, "did the file I read change" would compare against a different file than what gets written, meaningless either way. **This concurrency mechanism is only coherent after the legacy config path is fully retired** (already planned under this ADR's migration path) — it cannot be built correctly in parallel with that retirement, only after it.
- **Terminal behavior is not one policy.** Bounded retry (a handful of attempts, small random jitter, no exponential backoff — the remaining window is microseconds, not the kind of contention that benefits from backoff) followed by a clear, actionable error is right for *intentful* writes a user is actively waiting on (init, archive, add-category). It's wrong for incidental bookkeeping writes (the `lastUsed`-style timestamp bump, fts5 housekeeping) — those should be best-effort and silently skip on conflict rather than failing the user's actual operation over a write they didn't know was happening.
- **Rejecting OS-level locking, scoped correctly:** reject *advisory byte-range locks* (`flock`) specifically — genuinely inconsistent across POSIX/Windows — not lockfiles as a category. Git's own config-locking pattern (an atomic exclusive-create lockfile, `O_CREAT|O_EXCL`, written into, then renamed over the target) is portable and was a legitimate alternative worth naming even though it wasn't the mechanism chosen here; its terminal behavior (fail immediately with "another process seems to be running, remove the lock manually if not") is also a real, more conservative alternative to the retry-then-merge approach above, for the record. (`proper-lockfile` — a portable `mkdir`-based lock with staleness detection — was also considered; its cost, a killed process needing a timeout heuristic to detect a stale lock, is why optimistic merge was preferred here, not because portable locking doesn't exist.) One trap worth naming explicitly so it doesn't get proposed later: this project's SQLite dependency (`node-sqlite3-wasm`) is a WASM build with a plain Node `fs` VFS and no POSIX advisory locking — it does not provide a cross-process mutex, despite being tempting to reach for since it's already a dependency.
- **Adjacent gap, folds in for free:** `readConfig()`'s `JSON.parse` calls have no try/catch anywhere across all 17 call sites. Atomic writes prevent *new* corruption from this point forward but won't repair or gracefully report a file already truncated by the current unguarded-write code. Add a guarded parse that names the file path in its error, as part of this same change.

**Folded into the same design item, at the user's explicit request:** a related but structurally distinct risk — **two contributors on different branches independently assigning the same next sequential `ENH-NNN`/`issue-N` number.** Checked the KG for prior art before treating this as new: `issue-11` documents a deep investigation into the `ENH-NNN`/`issue-N` dual-taxonomy question and explicitly notes *"User independently recalls a deliberate discussion existed but confirms it is not recoverable from any available source — treated as lost, not resolved."* That's about *why two ID sequences exist*, not this exact race condition — so this may be the same lost institutional memory surfacing from a different angle, or a genuinely distinct, never-documented concern. Could not confirm either way; recorded here rather than assumed.

**Why this matters more than it looks today:** with the KG stored as markdown files in git, this collision is currently caught for free — two branches both creating `ENH-056` surface a real git merge conflict, forcing a human to look before it lands. That safety net is a property of *the storage medium*, not of any design in this project. If the KG's backing store ever changes to something the MCP server writes to directly and continuously — a database, a shared Notion workspace, a shared network folder — that free protection disappears entirely. Two processes could both silently claim the same ID at the same moment, and whichever write lands last silently overwrites the other's entry, with nothing forcing anyone to notice. **This risk scales in severity with exactly the kind of storage-backend flexibility [[ADR-066-kg-content-storage-location-for-global-and-cowork-modes]] and this project's broader roadmap already point toward** — it should be treated as a real design constraint on any future non-git-mediated storage backend, not a hypothetical.

**Not designed yet — this session recorded the requirement and its severity, not a chosen mechanism.** Candidate directions for a later pass: a compare-and-swap-style atomic claim on the next number (check-then-write as one operation, fail/retry on conflict) generalizes across both the file-locking and cross-branch-ID-collision cases and would work regardless of backing store. Left open, not decided.

**Mechanism resolved 2026-08-23**, in a dedicated brainstorming session (`v0.7.4.1-graph-numbering-conflict-gate`). Context for the resolution: no second contributor is active on this repo yet — this is forward-looking design, not a fix for an active collision. Three options were compared: (A) a contributor/feature prefix in the ID itself, (B) restructuring `decisions/`/`issues/`/`lessons-learned/` into per-contributor or per-feature folders, (C) keep flat sequential numbering and add a merge-time uniqueness check. **C was chosen** — A changes what the ID number means (no longer "the Nth decision," now "the Nth decision from this prefix"), and B carries real migration cost (71 ADRs alone) without actually removing collision risk (two people can still pick the same feature folder and number). C costs nothing to adopt and turns the *incidental* git-merge-conflict safety net (§ "Why this matters more than it looks today" above) into an *intentional* check — one that also catches the case a raw git merge wouldn't flag: two different slugs both claiming the same number, which merges cleanly as two distinct files.

Two further decisions, both approved the same session:

- **Detect + fix, not just detect.** The check doesn't only fail the build on a duplicate number — on collision it renumbers the later-created file to the next free number and rewrites every reference to the old number across the repo (filename, in-file header, entries in index files like `knowledge/enhancements/README.md`, and "Related:" cross-links in other ADR/issue/lesson files). **Tie-break rule: earlier commit wins the number; the later one is renumbered.**
- **Reuse, don't build new.** Folded into the existing manual pre-merge gate (the process behind commit `3b59ff3e`, "chore: pre-merge gate fixes — version sync, index counts, GitHub issue, backlinks") rather than standing up a separate script. That gate already scans `knowledge/` for the same *shape* of problem — stale index counts, missing backlinks — so a numbering collision is one more category of structural drift for it to catch, not a new kind of check. Two parallel gates risk silently diverging (one gets updated, the other forgotten); one gate keeps a single place to look.
- **Shared infrastructure, applied uniformly.** The same check runs identically across `knowledge/decisions/`, `knowledge/issues/`, and `knowledge/lessons-learned/` — one mechanism, not three bespoke ones, per the explicit requirement that a fix for one artifact type should share architecture with the others. This does **not** merge the three ID sequences or folder structures — they stay structurally separate, only the collision-detection-and-fix mechanism is shared.

Implementation plan: `docs/superpowers/plans/2026-08-23-v0.7.4.1-graph-numbering-conflict-gate.md`.

## Round 3 — Second Opus Gap Scan + Resolutions (2026-07-27)

Before continuing further down the original 14-item Opus review list, a second Opus scan was requested specifically to check for *new* gaps of the same "two reasonable rules collide" / "no defined trigger" shape — not a re-review of anything already resolved. It found 8 new candidates. Working through them one at a time:

**1. Personal KG doesn't exist yet — resolved.** No auto-create. Tell the user it doesn't exist, ask if they want to create it, then trigger the personal-init command — the same create-vs-select gate philosophy already established for the (now-descoped) topic-KG case, applied here to the personal KG's first-use case instead.

**2. "Path missing" conflating deleted/moved with temporarily unreachable — resolved.** Before ever asking "was it deleted or moved" (per the Round 2 fix to finding 6), check whether the *parent* directory is reachable at all first. An unmounted drive or sleeping network share means the parent is also unreachable — a different situation from a specific folder genuinely being gone, and shouldn't funnel into the same deleted/moved prompt.

**3. Moved-path repair colliding with an already-registered entry — resolved, with real pushback incorporated, not just accepted as proposed:**
- Tell the user the target already exists as its own registered entry.
- Offer a comparison before merging — but the original idea of pointing the user "outside the CLI" to manually read files was flagged as a stopgap, not a real feature. Building a real compare view is the better answer; punting to manual inspection is an accepted-for-now shortcut, not the permanent design. **Full mechanism resolved 2026-07-28** (fires as part of item 12's duplicate-`graphId` flow, after that item's content-divergence gate — not on every collision, since a fresh clone with nothing captured yet has nothing to compare):

  - **Comparison basis: relative file path + content hash, not filename or file-modified-time.** Verified against this repo's own real KG (690 files) that comparing by bare filename is actively misleading here: 22 filenames recur across unrelated folders purely because this project's own template scaffolding (`core/templates/`) gives every ENH/issue folder files with the same generic names (`specification.md`, `progress-log.md`, etc.) — two unrelated projects would show high "overlap" by name alone, false confidence in exactly the harmful direction. Relative path plus a content hash (measured cost: ~215ms for a 690-file/49MB KG — negligible, do it) instead yields four real categories: same path + same hash → identical (genuinely zero-risk); same path + different hash → **diverged, the load-bearing signal** or genuine fork evidence; path unique to one side → unique content; different path + same hash → moved/renamed unchanged (its own bucket, so it doesn't double-count as "unique" on both sides and inflate apparent divergence).
  - **File-modified-time is not a weak signal here, it's an inverted one — do not use it.** `git clone`/`checkout` resets every tracked file's mtime to the moment of cloning, which is exactly the scenario item 12's primary triggers describe (a freshly cloned "clean copy," a CI checkout, a re-clone mid-engagement) — meaning the newest-looking folder by mtime is reliably the one with the *least* real work in it, the opposite of what "most recently modified" implies to a reader. Use `git log -1 --format=%cI -- knowledge/` for git-tracked KGs instead (real commit recency, survives cloning; label it as git-derived), fall back to filesystem mtime only for non-git KGs (per item 12's G3 finding that personal/topic KGs aren't always git-tracked; label that too so the source is never ambiguous). Prefer a count ("N files touched in the last 30 days") over a single max-date — one stray editor save shouldn't swing the whole signal.
  - **Split unique-to-one-side content into recoverable vs. not.** Item 12 already confirmed large parts of `knowledge/` are gitignored in this project (`sessions/`, `chat-history/`, `plans/`, `me.md`, others) — content living only in those paths can never be recovered from git history if that folder's registry entry gets archived. This is simultaneously the highest-stakes content and the least attention-grabbing (session logs don't look important) — one `git ls-files` check per folder turns the view from purely informational into genuinely decision-bearing, the single highest-value addition to this mechanism.
  - **Presentation: fixed-size summary, not exhaustive lists.** A real KG can run into hundreds of files — dumping every differing filename into a chat window is unusable and gets lossily re-summarized by whatever AI client relays it anyway. Show full counts always, cap example filenames at ~5 with "(N more)," sort examples by most-recently-changed first, and lead with one plain-English verdict line — that's the part that actually reaches the user through the chat relay (e.g. *"Folder B looks like an older copy — nothing added since May, and only 2 files in it exist nowhere else."*).
  - **Worktree fingerprint, reported as its own line:** a genuine git worktree shows 100% identical tracked-file content with differences confined entirely to gitignored paths — a strong, nearly-free positive signal toward item 12's "this is a worktree" answer, independent of and complementary to that item's own worktree detection.
  - **Standalone tool, not only inline at `kmg-init`** — same correction item 12 already made for its own "mint new identity" action: a user who defers the decision and returns tomorrow needs to be able to see the comparison again, not just at the one moment the collision was first detected. Exposed as its own callable check (`kg_compare_graphs`), invoked both inline during item 12's flow and on demand later.
  - **Explicit handling for a missing/invalid target:** if a folder doesn't exist or isn't a valid KG (a stale moved-path target, for instance), state that plainly — reporting zero files for a path that simply isn't there would otherwise read as "empty, safe to discard," which is a different and much more dangerous claim.
  - **Minimum viable version, if this ever needs to ship in stages:** with the tracked/untracked split in place, six numbers alone (file counts per side, git-derived last-activity per side, changed-in-both count, only-in-B split into tracked/untracked) already answer the real decision — no filename lists required. Example filenames are a layer on top for extra confidence, not the core mechanism; the numbers alone are enough to unblock item 12's four-way choice.
- **"Merge" is scoped narrowly: registry entries only, not KG content.** A full content-level merge of two independently-numbered KGs would walk straight into the still-unsolved cross-branch ID-collision problem (Round 2, item 4) — two separate `issue-1`/`ENH-1`... sequences colliding on merge. Merging *only* the registry pointer (stop treating them as two separate registered paths, point at one going forward) avoids that; actual file-tree reconciliation stays a manual, human-led step, optionally assisted by the compare view above.
- **Dry-run required before any actual merge, with explicit approval.**
- **Bypass is allowed, but split into two independent axes, not one:** bypass skips *friction* (the dry-run/review step) — it must never skip *safety* (a backup/undo point is written regardless of whether the user bypassed review). Matches this project's own established pattern elsewhere (PR admin-override, `--admin` merges) and its own [[ADR-063-never-destroy-known-good-state-before-confirmed-write]] invariant (never destroy known-good state before a confirmed write) — overriding the review step is not the same request as overriding the safety net, and the design keeps them separate rather than letting one bypass imply the other.

**4. cwd changes mid-conversation — resolved.** Working in repo A, then `cd`-ing to repo B mid-session, then saying "capture that" correctly targets B by cwd-resolution rules — but flag it once, the first time cwd is noticed to have changed since the last call ("heads up, target's now B"), rather than following silently. Consistent with the "no name given → resolve from cwd, no confirmation" default for the common case, while still surfacing the one moment a user might not expect the target to have moved.

**⚠️ REOPENED 2026-07-27 by Fable review, two ways — (1) RESOLVED 2026-07-28, folded into item 1; (2) still open, see § Fable Review Findings item 5.** (1) "Flag it once" was ambiguous, but the bigger correction: **the "cd to a different top-level registered project mid-conversation" scenario this item was built around doesn't actually happen for Claude Code or Gemini.** The MCP server's cwd is fixed once at process spawn — nothing that happens inside a conversation afterward (including a `cd` run via the Bash tool) changes it, because the Bash tool runs in a separate process from the long-lived MCP server. To work in a different top-level project, a user opens a *new* session there (the 4-separate-processes pattern already confirmed empirically), not a `cd` inside an existing one. What *does* still happen within one session is moving between **nested KGs** (item 1) — e.g. `cd packages/api` inside an already-open monorepo — and that's where this item's flag now lives: fold into item 1's resolution, flagging when the *resolved KG* changes between nesting levels, not on every raw cwd move. (Codex remains a partial exception, per its `sandbox-state-meta` mechanism reading the live turn's cwd — a genuine per-turn location change may be possible there depending on Codex's own turn-context semantics.) (2) The precedence question against item 8 ("stay in personal" vs. a cwd change) is still open — see § Fable Review Findings item 5.

**5. Archived-entry ask-frequency — resolved.** Not a fixed policy (always-ask vs. once-per-session) — an explicit choice offered to the user at the prompt itself, with two distinctly labeled options so they aren't assumed interchangeable: **"Skip"** (just this one time — keep asking again on the next call) vs. **"Ignore"** (stop reminding for the rest of this session). "Always surface, never silent" (Round 2) still holds — this only decides how long an acknowledgment lasts once given, never removes the initial surfacing.

**6. `$HOME`/`/` as cwd — resolved, two-layer.** (a) **Identity check first:** confirm the session's actual OS user matches who owns that home directory — mismatch means warn or stop, not proceed, tying into the security gap the first Opus review flagged (finding 12). (b) **If it is genuinely the user's own home dir:** since Claude Code/Codex/Gemini sessions are normally opened from inside a project folder, a session actually sitting at `$HOME` is unusual enough to be a deliberate signal — so ask plainly, matching the format used throughout: *"You're currently in your own home directory — is this for your personal graph, or one of your existing registered projects?"* Never silently default to personal just because home is a path-ancestor of the personal KG's storage location.

**⚠️ REOPENED 2026-07-27 by Fable review — layer (a) breaks on CI/shared machines.** On a build server or container where everything runs as one system user (`root`, `runner`, `ci`), every session trivially "owns" `$HOME` — the identity check produces zero signal in exactly the automated context most likely to have unrelated jobs colliding. Fable recommends scoping the identity check to interactive/human sessions only, and requiring an explicit `scope` param (no inference at all) for anything automated. See § Fable Review Findings below.

**7. Registered path exists, KG content folder missing — resolved.** Never silent, always ask — but investigate before asking, the same philosophy as finding 2 above (check parent reachability before assuming deleted/moved): if this is a git repo, check other branches/git history first to see whether the content previously existed, was moved, or renamed within git, before presenting the user with a bare "it's missing, want me to recreate it?" prompt.

**8. Ephemeral personal-scope preference — scope and expiry, resolved.** Applies to **both reads and writes** — write-only scoping would leave "what did I note about X?" silently searching the project graph, exactly the "shouldn't have to think about which graph is active" burden this design exists to remove.

**⚠️ REOPENED 2026-07-27 by Fable review — no precedence rule against item 4 above.** If a user says "stay in personal" then `cd`s to a different repo mid-session, this item and item 4 (cwd-change flag) were resolved independently and never cross-checked: does the cwd-change flag silently override "stay," or does personal persist regardless of cwd? See § Fable Review Findings below — not yet decided.

Rather than guessing at auto-clear triggers, **the intent is asked up front, explicitly, the first time personal scope is invoked**: *"Is this a one-shot to your personal graph, or do you want me to keep working there until you tell me otherwise? If you don't say to leave, I'll stay."* This makes indefinite persistence within a session an informed, explicit choice rather than a silent default nobody remembers opting into — and eliminates the need for any auto-clear heuristic (cwd change, call count, etc.) entirely, since the user was told plainly what "stay" means when they chose it. An optional companion shortcut: a prefix at the start of a message for a fast one-shot without repeating the up-front question every time, analogous to how a status line shows current repo context at a glance in Claude Code/Codex/Gemini today.

**Marker syntax resolved 2026-07-28: bracket prefix, `[personal]` / `[project]`.** Rejected a bare word (`personal`, `mygraph`) — same failure class already documented for [[ENH-055]]'s trigger-vocabulary gap: ordinary conversation containing the word "personal" (e.g. "check my personal notes") could misfire as a scope directive with no delimiter to distinguish intent from topic. Rejected a dash/CLI-flag style (`-personal`/`--personal`) for the same reason in a different shape — dashes appear constantly in ordinary prose (em-dashes, hyphenated words), so a dash-prefix only stays unambiguous if parsed strictly as the first token of a message, unlike a bracket which essentially never appears in natural writing. Rejected slash-command style (`/personal`) outright — that namespace already means something else (real slash commands) on the platforms this project targets; reusing it here would collide with existing user expectations, not just be stylistically off. **Symmetry:** `[project]` added as the explicit one-shot-back counterpart — no reason switching to personal gets a shortcut and returning to project scope doesn't.

**Documentation impact, explicit:** this is new user-facing syntax, not an internal mechanism — the `docs/` reference and guide pages covering personal-scope usage must be updated to document `[personal]`/`[project]` when this ships, per this project's own CLAUDE.md rule ("Docs updates: Update affected reference and guide pages when behavior changes"). Flagging inline here so it isn't lost between this ADR and whichever branch eventually implements it.

**Known residual risk, per Opus:** if the conversation is compacted/summarized mid-session, this ephemeral, never-on-disk preference could quietly drop without anyone noticing, silently reverting writes to project-local. Echoing the resolved target on every write (already established elsewhere in this design) makes that visible after the fact, but doesn't prevent it — flagged, not solved, here.

### A. Items previously marked "resolved" that need revisiting

1. ~~Item 7 (nested project-local KGs disallowed entirely) — real pushback, not a nitpick.~~ — **RESOLVED 2026-07-28: allow nesting, deepest-registered-path-wins.** Item 7's blanket ban is reversed. The user's original concern was complexity, not principle — the user asked for a joint solution from Claude, Opus, and Fable specifically to check whether nesting could be accommodated *without* adding real complexity before agreeing to it.

   **Final design, folding in both models' corrections:**

   - **The tiebreak is not "none."** Two registered paths that normalize to the exact same location *are* item 12's duplicate-registration case, not a separate problem — item 12's `graphId` identity marker is precisely the mechanism that resolves a true tie.
   - Both the registration-time rejection check and item 7's own defensive-remediation flow (for pre-existing/hand-edited nested state) are removed entirely — no longer needed once nesting is allowed by design.

12. ~~Accidental duplicate registration of the same physical KG.~~ — **RESOLVED 2026-07-28, fully specified after a second Opus pass surfaced the initial design was incomplete.** A repo cloned to two different paths and `kmg-init`'d twice (contractor "clean"/"working" copies, CI checkout dirs, re-cloning a client repo mid-engagement) produces two independently-numbered registry entries for what's conceptually one KG — hitting the cross-branch ID-collision problem (§ Round 2, item 4) from a trigger this document never named. No identity marker of any kind exists today (verified: no `uuid`/`graphId`/equivalent anywhere in `mcp-server/src`).

    **Two empirical corrections that shape the whole design, verified against real code:**
    - **The registry is a map keyed by name, not a list** (`mcp-server/src/utils.ts:29` `KgConfig`, `utils.ts:88` `config.graphs[config.active]`). Every collision involves two distinct *names* as well as two paths — an earlier draft of this resolution treated merge as a path-only decision, which was wrong.
    - **Forks are not actually indistinguishable from clones.** A GitHub fork has a different `origin` remote URL from the moment it's cloned — a free, reliable discriminator the original design ignored entirely.

    **Base mechanism:** a `graphId` marker lives in the KG's own content directory (`knowledge/`, git-tracked when the KG is git-tracked), not in the local registry entry — committed once, travels automatically with every clone/checkout of that history, the same way any tracked file propagates. At `kmg-init`, check for a `graphId` already present in another registered entry; if found, surface it rather than silently creating a second independent registration. This also resolves § Round 3 item 3's moved-path-vs-existing-entry identity question and gives that section's proposed compare-view a real join key.

    **Merge target resolution — two separable questions, not one.** Because the registry is name-keyed, a merge must resolve which *path* is live and which *name* survives as the map key — these are independent. **Ask only about path** (never auto-pick); **default name to the pre-existing entry** and state that default plainly in the prompt, since names are how users target a graph explicitly elsewhere in this design (§ Resolution flow steps 2-4) and appear in session summaries, scripts, and prior captures — silently discarding one breaks all of those. **Gate the question on actual content divergence** — if the newly-registering copy has no captured content yet (the common case: fresh clone, `kmg-init` immediately), there's nothing to merge and no question needed, just a silent re-point. **Automated-mode branch, per § D:** every ask in this design routes through one gate with a bounded timeout; this is no exception — `{"error": "KMG_INPUT_REQUIRED", "reason": "duplicate_graph_id", "resolveWith": {"param": "canonicalPath"}}`.

    **Losing-folder fate — archive, never delete.** The registry already has an `archived` status with machinery built specifically for "surface, never silently fail" (§ Registry lifecycle; item 7 above extended the same enum with `pending` precisely to reuse this). **Archive the losing entry with a `mergedInto` pointer instead of removing it**, and **keep its name resolvable as an alias to the surviving entry** rather than letting it go dead. Consequences: a session landing in the archived folder gets "this path was merged into X on `<date>`" — self-explaining — instead of a bare "not initialized" the user has to reverse-engineer; it preserves the append-mostly registry invariant item 4 above already established (removing `lastUsed` rather than grandfathering a violation — deleting entries on merge would violate the same invariant one item over); and it makes the merge reversible, satisfying Round 3 item 3's "safety net written regardless of whether review was bypassed" without a separate backup mechanism. Keep the plain-language warning at merge time too — with archiving in place it stops being the only thing standing between the user and a confusing dead end.

    **The fork case — four answers, not two, at `kmg-init`'s duplicate-`graphId` prompt:**
    1. **Reattach** (same project, genuinely a duplicate registration) — routes into the merge mechanism above.
    2. **Worktree / deliberate linked copy** (same repository, same history, legitimately meant to coexist — e.g. a git worktree, which this project's own tooling already assumes exists via `superpowers:using-git-worktrees` and the `Agent` tool's `isolation: "worktree"` mode) — records `duplicateOf` and **suppresses the warning permanently for that specific pair**, without merging or re-minting anything. This was the single most likely false positive the original two-answer design would have produced, on every worktree creation, unaccounted for.
    3. **Intentionally separate project** (a real fork meant to become its own independent KG) — **mints a fresh `graphId` immediately**, so it stops colliding with the original on every future check. This write dirties the fork's working tree with a change the user didn't make; the mint must say so plainly and offer to commit it, or the collision returns on the next clone of the fork. The marker file itself must be authored to self-resolve a future git conflict for a non-technical reader — a one-line comment such as *"if this conflicts during a merge or sync, keep your side — this file just identifies your copy of the graph."* **This action must be reachable after the fact, as its own standalone step, not only at the one moment `kmg-init` happens to run** — a fork's `knowledge/` directory typically already exists, so init may short-circuit as "already initialized" and never reach the prompt at all.
    4. *(Decline / not sure)* — no forced choice; defer, ask again next `kmg-init` run.

    **Ordering signal: use the git remote, captured once at registration.** Same `graphId` + different `origin` → lead with option 3 ("separate project?"). Same `graphId` + same `origin` and same path-lineage → lead with option 2 ("worktree?"). Same `graphId` + same `origin`, different path, no worktree signature → lead with option 1 ("reattach?"). This turns a genuinely ambiguous prompt into one with a well-ordered default, for the cost of one `git remote get-url origin` call. **The origin URL is recorded for this discriminator only — not for reconciliation.** Stated explicitly so a later reader doesn't mistake the field for an unfinished sync feature; post-merge git divergence between two already-merged folders remains explicitly out of scope, consistent with the boundary already locked in under Round 3 item 3 (file-tree reconciliation is a manual, human-led git operation this design does not automate).

    **Three additional gaps found during verification, high enough impact to fold into the base mechanism rather than leave as residual risk:**
    - **Selective `.gitignore` can silently void the entire mechanism.** Verified live in this repo: parts of `knowledge/` are already gitignored (`knowledge/plans/`, `knowledge/sessions/*`, `knowledge/me.md`, `knowledge/chat-history/`, `knowledge/tmp/`, others). The "committed once, travels automatically" property holds only if the marker's own path escapes the user's ignore rules — if it doesn't, the mechanism produces no error and degrades to nothing: every clone just looks like a brand-new graph forever, silently. **Mitigation: verify the marker is actually tracked at write time** (`git check-ignore` / `git ls-files`) and warn if it isn't.
    - **Template/scaffold tooling would propagate identity into unrelated projects.** This project ships `core/templates/` and a live `kg_scaffold` tool; bootstrapping a new KG by copying an existing `knowledge/` directory would carry the source graph's `graphId` into a completely unrelated project. The strip-or-re-mint rule from option 3 above must attach to scaffold/copy code paths too, not only `kmg-init`.
    - **The marker isn't only a git artifact.** Per ADR-066's taxonomy, personal and global-topic KGs may not be git repos at all (this repo's own `knowledge/me.md` is itself gitignored) — yet `graphId` is load-bearing beyond propagation: it's item 1's true-tiebreak and the join key for Round 3 item 3's compare view. **The marker is always written, regardless of git status; git-tracking is what makes it travel automatically, not what makes it exist.**

    **Two smaller notes, recorded rather than designed further:** detection only ever sees *registered* graphs — the honest meaning of the warning is "already registered at X," not "already exists at X"; the most common real accident (re-clone, work in it, never run `kmg-init`) is invisible to this check but already hard-fails safely under this ADR's existing un-init'd rules, so prompt wording should say "registered," not overclaim. And the marker write must be **strictly idempotent** — re-running `kmg-init` on an already-marked graph must be a guaranteed no-op on the marker, since a re-init that re-mints would create a second identity for one graph, the exact failure this item exists to prevent, introduced by its own fix.

    **Scope boundary, clarified:** registry entries are per-machine, local-only (`~/.kmgraph/kg-config.json`, never committed) — two clones on the *same* machine trigger the warning; two clones on *different* machines (e.g. contractor laptop + a client's CI runner) never collide locally, and don't need to, since neither machine's registry is aware of the other's. **This mechanism intentionally does not decide which clone is "authoritative."** Content authority stays exactly where git already puts it — whichever branch/commit reaches the shared remote. The fix only prevents local registry-bookkeeping confusion (two path entries pointing at what's really one graph); actual file-tree reconciliation between diverged clones stays a manual, human-led git operation, same boundary already locked in under Round 3 item 3 (merge is registry-pointer-only, never KG content).
13. ~~No way to browse activity across many registered KGs.~~ — **RESOLVED 2026-07-28: descoped from this ADR, same YAGNI treatment as [[ENH-053]]/[[ENH-054]].** Original framing (team lead on a shared machine wanting "what did the last few contributors log") doesn't match how this project's actual user works — solo, multiple client repos, not a shared-team machine. Splitting what got blended together clarifies why: **(1) cross-project bleed risk from a shared login is already fully prevented** by items 1-12 of this ADR (cwd-based resolution, hard-fail on un-init'd repos, first-time-seeing-a-repo confirmation, contractor-isolation never-fall-back-to-personal) regardless of how many different people's projects sit in one machine's registry — a bulk-browse tool isn't needed to prevent that, it's already structurally prevented. **(2) The sharper real case surfaced during this discussion — hot-desking / shared-login accountability in a regulated or office environment (e.g. a federal contractor forced to share a desk or log into a shared machine)** — is a genuine "who touched what, when" audit need, but that's a different problem than KG resolution, and this project already has a home for it: **[[ENH-054]]**, the full audit-trail history log for registry transitions, already deferred earlier in this same ADR as YAGNI'd-for-now. ### D. Items 3 + 8 — Resolved 2026-07-28: one interactivity discriminator

Independent parallel research (Opus + Fable, same brief, no cross-visibility) was commissioned specifically for these two items, since both reduce to the same missing primitive: **can the MCP server tell, per call, whether there's a human able to answer a question right now, or not?** Both models converged on the same shape; Opus additionally surfaced two live facts that changed the design (verified independently below, not taken on faith).

**Verified facts (web-confirmed 2026-07-28, not assumed):**
- **Gemini CLI cannot use MCP elicitation at all** — throws `Method not found`. Open bug, filed 2026-03-13, unresolved as of today: [gemini-cli#22249](https://github.com/google-gemini/gemini-cli/issues/22249).
- **The MCP spec itself shipped a rewrite today (2026-07-28)** removing the old `initialize` handshake and blocking-style elicitation, replacing both with a stateless `InputRequiredResult` — server returns "I need more info," client retries the same call with the answer filled in. [MCP 2026-07-28 Release Candidate](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/), [Key Changes](https://modelcontextprotocol.io/specification/draft/changelog).
- Consequence: the `InputRequiredResult` return-and-retry shape isn't a Gemini-specific workaround — it's about to be the standard mechanism for every MCP client. **Design decision: build only this one path. Do not build native blocking elicitation at all**, for any client — one code path, forward-compatible with where the protocol is going, and it happens to work on Gemini today for free.

**The discriminator — resolved per tool call, never cached (consistent with this ADR's existing no-caching invariant, `utils.ts:51`):**

Precedence, first match wins:
1. Explicit per-call param (`interaction: "interactive" | "automated"`)
2. Explicit env override (`KMG_INTERACTION=interactive|automated`, same pattern as existing `KG_CONFIG_PATH`/`CLAUDE_PLUGIN_ROOT`)
3. CI environment detected (`CI` truthy plus the standard list: `GITHUB_ACTIONS`, `GITLAB_CI`, `CIRCLECI`, `JENKINS_URL`, `BUILDKITE`, `TF_BUILD`, `TEAMCITY_VERSION`, `BITBUCKET_BUILD_NUMBER`, `CODEBUILD_BUILD_ID`, `DRONE`, `APPVEYOR`, `HEROKU_TEST_RUN_ID`) → `automated`. Truthiness excludes `0`/`false`/`no`/`off` case-insensitive — `CI=false` must NOT mean automated (CRA's docs tell people to set this).
4. Client can accept an `InputRequiredResult` retry at all (practically: everyone, once the D-above simplification lands) and no CI signal → `interactive`
5. Otherwise → `automated` (fail-closed default)

Never used as a signal: `clientInfo.name` (spoofable, identical between `claude` and `claude -p`), container/Docker detection (devcontainers and Codespaces are humans, not CI).

**Explicit-beats-ambient, with one exception:** a param/env claim of `interactive` cannot be honored if the client genuinely can't be asked anything (no capability to accept the retry shape) — downgrades to `automated` with a machine-readable reason. An override grants permission to ask; it can't manufacture a channel to ask on. If CI is detected AND an explicit `interactive` override is also set, the override wins but a visible warning is included in the result (guards against a copy-pasted override left in a CI script).

**Mandatory safety net:** every question has a bounded timeout regardless of detected mode. Expiry → cancel, return structured error, no partial write. This is what makes the scheme safe under a wrong guess, not just correct on average — covers the one case detection can never solve (a human runs a script from their own terminal, unattended, indistinguishable from `interactive` by any available signal).

**Rejected: bare `confirm: true`/`--yes`.** Can't answer "which of these 3 fuzzy matches" with a boolean. Automated callers instead pass the actual answer as an explicit param (`scope`, `graph`, `confirmFirstUse`, `confirmMigration`, ...); any branch missing one returns a structured error naming exactly which param resolves it (e.g. `{"error": "KMG_INPUT_REQUIRED", "reason": "ambiguous_home_cwd", "resolveWith": {"param": "scope", "accepts": ["user","project"]}}`).

**How this closes item 3:** the file-ownership identity check only runs when mode is `interactive`. In `automated` mode, `$HOME`/`/` as cwd isn't a question at all — immediate structured error requiring explicit `scope`. The vacuous-check-on-shared-CI-machines problem disappears by construction; the check itself was never the right primitive.

**How this closes item 8:** every "ask the user" branch in this design (fuzzy match, archived entry, first-time-repo, nested-KG conflict, personal-KG-missing, moved-path merge, `$HOME` ambiguity) routes through one gate function. No branch can hang, because none can ask without passing through the same mode check + timeout.

**Four new cross-item bugs found during this research, not previously seen anywhere in this document — folding directly into their originating items rather than re-opening them separately:**
- **Item 7's `pending → active` first-use flip** (§ A above): an automated caller performing that flip silently consumes the one-time human confirmation item 12(a) exists to guarantee. Fix: automated callers never flip `pending → active` themselves — they get `reason: "first_use_repo"`, must pass `confirmFirstUse: true`, and the flip records `confirmedBy: "automated"` so an interactive session still surfaces it once later.
- **Round 3 item 8's ephemeral personal-scope "stay"** has no meaning for an automated caller (no standing conversation to persist within) — disabled entirely in `automated` mode; `scope` is per-call only there.
- **Migration (`kg_upgrade`)** was specified to require explicit human consent + backup — never checked against automated callers. Refuses without `confirmMigration: true`; backup is written regardless of whether review was bypassed (same friction-vs-safety split already adopted for Round 3 item 3's merge design).
- **Reads, not just writes** (`kg_search` etc.), must also hard-error on ambiguity in `automated` mode rather than silently resolving — matches this document's own established read/write symmetry principle (Round 3 item 8).

## Cross-Tool Note: Bash Tool Persistent-cwd Drift (2026-07-29) — context, not yet planned

Raised while working a different session (`docs-readme-poc`): the Bash tool's own documented behavior is that "the working directory persists between commands, but shell state does not." If any Bash call in a session runs `cd` into a different repo (a subagent, a workflow step, a test harness invocation), every subsequent relative-path Bash command in that same session silently operates against the wrong repo until something `cd`s back — with no warning and nothing distinguishing it from the correct repo.

**Same failure shape as this ADR's core concern, different layer.** It's not `.active`/kg-config drift — it's a shared, mutable, easy-to-forget piece of *session* state (the Bash tool's persisted cwd) that a later, unrelated action can silently change, and every subsequent command trusts without re-checking. Unlike `.active`, this can't cross-contaminate *between* sessions — it's scoped to one session's Bash tool state — but it can cross-contaminate *within* one session once any step `cd`s elsewhere.

**Not planned/designed — captured as context only.** No decision made on whether/how this should factor into the kg-resolution model above (e.g., whether `kg_*` tool handlers should re-derive/re-verify their own cwd on every call rather than trust an ambient value, which the resolution flow already does by re-reading the registry fresh per call — the same principle may already cover this, but it hasn't been explicitly checked against this specific drift mechanism). Flagging for whoever picks up planning next, not resolving here.

## Known Gap — `gov-capture-routing` Overlap and a Security Bypass, Found During Phase 6/7 Implementation (2026-08-03)

Surfaced while implementing this ADR's Phase 6/7 on `v0.7.0-adr-067-c1`, unrelated to what either phase set out to do. **This ADR never referenced or was aware of `gov-capture-routing`** — confirmed by grep, zero hits for that string anywhere in this document before this section.

**The overlap.** `gov-capture-routing` is a pre-existing skill, unrelated in origin to this ADR, designed under [[ADR-034-capture-level-routing-dispatcher-agent-split]] to detect "personal vs. project vs. named vs. active" capture-level intent from natural language and resolve `$level`/`$target_kg`/`$target_path`/`$restore_kg` for the commands and agents that call it. It's referenced by 5 commands (`kmg-session-summary.md`, `kmg-recall.md`, `kmg-capture-lesson.md`, `kmg-create-adr.md`, `kmg-sync-all.md`), 3 agents (`agents/create-adr-agent.md`, `agents/lesson-capture-agent.md`, `agents/session-summary-agent.md`), and one skill (`skills/kmg-auto-recall/SKILL.md`). It has been non-functional/unreachable via the Skill tool for 3+ months — tracked as **issue-18**, filed well before this ADR-067 work began, with its "fix vs. retire" question left open.

This ADR's work has now functionally subsumed both things `gov-capture-routing` existed to do, as a side effect of pursuing its own unrelated goal, not as a design intent:
- **The switch/restore half**: Phase 6 retired `kg_config_switch`/`kmg-switch.md` entirely (this ADR's core goal), and `commands/kmg-sync-all.md`'s restore-step contract was rewritten during Phase 6's doc sweep to state "No switch/restore needed."
- **The level-detection half**: `kg_capture` gaining a `scope: "project"|"user"` param (added purely for consistency with `kg_search`/`kg_config_add_category`/`kg_fts5_status`/`kg_fts5_rebuild`/`kg_upgrade`, which already had one) plus `[personal]`/`[project]` marker parsing (Phase 6) and cwd-derived resolution (Phase 1) means a calling command can now pass `scope`/`targetKg` directly to `kg_capture` instead of needing a routing skill to pre-resolve intent from natural language first.

**A concrete security bug, found while investigating the overlap.** Three of the agents that reference `gov-capture-routing` (`create-adr-agent.md`, `lesson-capture-agent.md`, `session-summary-agent.md`) also have a separate `--user` code path that bypasses `kg_capture` entirely — it writes directly via the Write tool to `~/.kmgraph/{decisions,lessons-learned,sessions}/`, with **zero confirmation gating**. This sidesteps `confirmPersonalScopeAccess`/`confirmFirstWrite` — the exact gates Phase 6 of this ADR built specifically to guard personal-scope writes. The bypass predates this ADR (it existed because `kg_capture` previously had no path to the personal graph at all), so it isn't a regression this ADR introduced, but it is now both obsolete and a live security hole, since the gated path it was working around now exists.

**Consequence for this ADR's scope.** A new **Phase 7.1** (`knowledge/plans/v0.7.0-adr-067-p7.1.md`) is being added to close this gap: remove the dead `gov-capture-routing` invocation from the 5 commands + 1 skill above, and remove the `--user` Write-tool bypass from the 3 agents above, routing all capture-level resolution uniformly through `kg_capture`'s `scope`/`targetKg` params. This formally resolves issue-18's long-open fix-vs-retire fork as **RETIRE** — a direct, if unplanned, consequence of this ADR's own resolution model making the routing skill's job redundant.

**Correction after independent review (2026-08-03), before Phase 7.1 executed:** the "functional subsumption" framing above oversold how clean the replacement is, and the security-bypass framing above was incomplete. Two things a review pass caught, folded into Phase 7.1's plan before any of it ran:
- The 3 agents' `--user` bypass is not the only Write-tool escape hatch — each also has a separate "MCP unreachable/failed" fallback that, once the `--user` bypass is closed, would become reachable for `scope:"user"` writes too (same zero-gating problem, different trigger, and it targets the wrong graph — the project-local KG, not personal). Phase 7.1 Task 7.1.1 now explicitly closes this second path too.
- `gov-capture-routing`'s actual skill file (`~/.claude/skills/gov-capture-routing.md`, real and complete, just unshipped/unreachable) has real capability beyond a flag-to-scope mapping — richer NL trigger vocabulary, conflict-resolution with a persisted per-file preference, and multi-capture-in-one-message handling. Phase 7.1's replacement does not reproduce any of that. Since the skill was never actually reachable in 3+ months of production use, this isn't a regression against real behavior, but it is a real, conscious narrowing of [[ADR-034-capture-level-routing-dispatcher-agent-split]]'s original design intent — Phase 7.1 now says so explicitly rather than implying lossless subsumption.
