# issue-32: Already-running MCP server processes silently keep serving stale plugin code after an upgrade

## Problem

`kg_upgrade`'s version-sentinel mechanism (ADR-055) correctly detects when an installed plugin version is ahead of what a graph last applied, and surfaces a `version-update` item at session start. What it does not cover: a session that was **already open** before the upgrade landed keeps running the *old* code indefinitely after the upgrade completes, because Node.js processes don't hot-reload — only a fresh process picks up new code on disk.

Confirmed live, same-day, same-instant repro (2026-07-28):

- Before running `/plugin` update + `/reload-plugins`, `kg_version` in this session reported `installed: "0.3.10"` — itself a symptom of the stale-legacy-config-path bug this ADR set documents (issue-14), not the actual installed plugin version.
- After running `/plugin` update then `/reload-plugins`, the same tool call in the same session correctly reported `installed: "0.6.20"` — confirming a session's own process *does* pick up new code after an explicit reload.
- A process listing taken at that same instant showed **6 of 8 live `mcp-server/dist/index.js` processes still running from `.../kmgraph/0.6.16/...`**, unaffected by the reload — only the two sessions that actually ran `/plugin` + `/reload-plugins` got new processes. Every other open session, across other terminals/IDEs, keeps serving 0.6.16 indefinitely with no signal that it's now behind.

## Why this matters

This is a plausible root cause for real split-brain incidents already documented elsewhere in this KG (see ADR-067 § Live Split-Brain Caught Mid-Session) — a long-running process silently executing outdated resolution/config logic looks identical, from the outside, to a config-file staleness bug, but has a different fix.

## Scope

This is a code-staleness problem (is the running process current with what's installed on disk), not a KG-resolution problem (which graph does a call target) — explicitly out of ADR-067's scope. It belongs with ADR-055's version-sentinel mechanism, which already governs "does this installed version differ from what a graph last applied" — this is the adjacent, previously-unhandled case of "does *this specific running process* differ from what's now installed."

## Cross-platform research (2026-08-01, corrected 2026-08-01 after independent Opus review)

Prior art confirms this is a known class of bug, not unique to this codebase:

- **`claude-mem`** (thedotmack/claude-mem, a real Claude Code plugin) hit nearly the same bug — see issue #2246: stale MCP server processes from old plugin versions **accumulate unboundedly** on Windows (4 live processes from v8.5.2 still running months later). Genuinely strong, directly-relevant prior art for the "already-running processes silently keep serving stale code" symptom. **Correction (2026-08-01): the "mtime-ranking was unreliable, switched to a semver version-oracle" and "stale process respawned itself in a forever-loop" claims previously recorded here are not supported by the actual source — independently verified against PR #2394's full diff (touches `ChromaMcpManager.ts`/`ClaudeProvider.ts`/`EnvManager.ts`/build hooks/tests, no version-resolution or mtime-ordering code) and #2246 itself. The nearest real item is an unrelated API-retry-loop fix (#2357), not a self-respawn loop. Do not cite claude-mem for either the mtime lesson or the self-restart-loop lesson — only for the accumulation symptom itself. #2246's real fix direction (#2377) was canonical `${CLAUDE_PLUGIN_ROOT}` spawn-contract templating — a path-resolution fix, not a version-detection one.**
- **Claude Code's own plugin system** has update-notify + `/reload-plugins`, which hot-reloads MCP servers in-process with no restart required — but this only covers Claude Code's first-party plugin/marketplace layer, not generic third-party MCP servers like this one. The desktop app lacks `/reload-plugins` parity (issue #52967). MCP's own `notifications/tools/list_changed` mechanism exists but is inconsistently honored — Claude Desktop is non-compliant per issue #50339 — so it isn't reliable as a sole mechanism.
- **Gemini CLI**: no self-staleness detection found. `--auto-update` extensions require a full restart to take effect (issue #21392).
- **Codex CLI**: no self-staleness detection found. Multiple open, unfixed bugs of the same underlying class: stale `config.toml` MCP paths after auto-update (#26011), no `tools/list_changed` cache invalidation (#33266), leaked stale MCP wrapper processes (#17115).
- **Cursor**: no built-in convention for this. "Reload MCP Server" is reported unreliable; the community has built an unofficial fix extension to work around it.
- **General Node.js patterns**: `nodemon`/`pm2` watch-mode restart-on-any-touch patterns are dev-time-only conventions, not safe for a process that may be mid-request — not a fit here.
- **Local prior art already installed on this machine**: the `claude-hud` plugin's `version.js` resolves the real Claude Code binary from PATH, `fs.statSync`s it for `{path, mtimeMs}`, and uses that pair as a cache key — the expensive real version check only reruns when the pair changes — persisting the cache to disk as JSON so it survives across restarts. This is the concrete pattern adopted in the resolved design below.

## Resolved design (2026-08-01, corrected 2026-08-01 after independent Opus review found a blocking defect)

**Never self-restart — conclusion unchanged, reasoning corrected.** On detecting its own code is stale, the process only surfaces a warning — it never attempts to respawn or restart itself. Not because of claude-mem's (misattributed) loop bug, but for a stronger, structural reason: **an MCP server's process lifecycle belongs to its host, not to itself** — the host holds the stdio pipes to a specific PID, and a server that exits and tries to respawn breaks that transport outright. This isn't a risk tradeoff to weigh, it's a protocol-layer constraint. Mid-tool-call restart would also destroy in-flight work in a live coding session regardless. An external-bootstrapper alternative (a separate tiny process doing the respawn) was considered and rejected — it dodges the self-resolver trap but not the transport-ownership problem, and adds a second process to lifecycle-manage for no benefit over just warning.

**BLOCKING DEFECT FOUND AND FIXED: the original "self-stat own entry file" cache key cannot work.** Verified against the real on-disk layout on this machine: installs are **version-pinned sibling directories** (`.../kmgraph/0.6.16/mcp-server/dist/index.js` and `.../kmgraph/0.6.20/mcp-server/dist/index.js` coexist; an upgrade writes a new directory and never modifies the old one). A process running from `0.6.16` sees the same path and the same mtime for its own entry file for its entire lifetime — the cache key is invariant, so the check can never fire. This is exactly the case documented in this issue's own repro above (processes still running from `.../kmgraph/0.6.16/...` after upgrade). The `claude-hud` pattern actually works because it stats the `claude` binary **freshly resolved from PATH on each check** — an indirection that repoints on upgrade; statting your own already-resolved entry file has no such indirection, and that's the one piece the earlier draft of this design dropped while copying the caching pattern.

**Corrected mechanism:**
- At startup, capture the server's own version from its own baked-in `package.json` (immutable for the process's lifetime — this is "what version am I").
- Separately, on each check, resolve the **currently-installed** version independently of the path this process is running from — read the marketplace/plugin manifest, or scan sibling directories under the plugin cache root and take the max by parsed semver (never by mtime, never by string sort — this project ships `0.6.9` alongside `0.6.20` and a naive sort would get that wrong).
- Cache key = `(resolved-manifest-or-sibling-scan path, mtime)` of *that* lookup — not of the running process's own file. This restores the indirection that makes the pattern actually detect change.
- **Comparison semantics, stated explicitly:** `installed_version > running_version` → warn. `installed_version < running_version` (a local dev build, or a genuine downgrade) → stay silent; this is deliberate, not an oversight — flagging it here so a future reader doesn't "fix" it into warning both directions.
- Check lazily on every tool call (a single cheap read of the resolved pointer), not via a file-watcher — `nodemon`/`pm2`-style continuous watching is a dev-time pattern and risks triggering mid-request.

**Warning channel — decided, not either/or.** The warning is embedded in the tool response as an explicit instruction addressed to the assistant to relay to the user verbatim (not a stderr log line — invisible to the user on every host considered). It must say plainly that *the user*, not the assistant, has to act — the assistant calling the tool cannot fix a stale process itself, only the user restarting/reloading can. Stderr rejected as the sole channel for this reason. Timing is self-consistent: since the check runs exactly when a tool is called, there's no window where staleness is detected but has nothing to attach the warning to.

**Dedup with ADR-055 — open, needs a decision before implementation, not deferred silently.** ADR-055's sentinel already surfaces a `version-update` item at session start (disk-state vs. what-a-graph-last-applied). This mechanism would additionally warn mid-session, from a different signal (this-process vs. what's-now-installed). Whether both fire independently, or this mechanism suppresses itself when ADR-055's sentinel already covers the same case, is not yet decided — record as an open design question for the implementation plan, not something to guess at silently.

**Resolved (2026-08-01): no suppression — both mechanisms fire independently.** See `knowledge/plans/v0.7.0-c4-issue-32-stale-mcp-warning.md` § Global Constraints. ADR-055's sentinel fires once per session start on a different signal (disk-installed vs. what a *graph* last recorded as applied); this mechanism fires per-tool-call on a different signal (disk-installed vs. what *this specific process* is running) — a session can be stale on one axis without the other, so suppressing either on the other's presence would hide a real, independent signal. The plan's Task 6 adds an addendum to ADR-055 § Known Gap documenting this, and separately fixes a real label collision it surfaced: ADR-055's existing `checkVersionMismatch` prints the *running* process's own baked-in version but labels it "Installed" — on exactly the stale-process case this issue targets, that string and this mechanism's warning would show two different numbers both labeled "installed." Task 6 relabels that string to "Running" to remove the collision.

**Platform-branching claim, narrowed.** *Detection* needs no platform branching — confirmed none of Claude Code, Codex, or Gemini provide this for third-party MCP servers, and all three spawn this server as a subprocess with normal filesystem access. *Remediation instructions in the warning text do need to differ by host*, per this doc's own citations: Claude Code has `/reload-plugins`; Gemini (#21392) and Codex need a full restart; Claude Desktop lacks `/reload-plugins` parity (#52967). The warning text must select the correct remediation instruction for the calling client, not state one universal instruction.

**Explicitly out of scope, stated rather than left silent:** this mechanism warns per-stale-process; it does not reduce the *count* of stale processes accumulating (the actual complaint in claude-mem's #2246, and this issue's own repro shows 6 of 8 processes stale). Cleaning up/killing old stale processes is a different, separate fix — not designed here.

**Test strategy (named deliverable, not optional):** this bug only exists across an upgrade boundary — a test fixture with two real sibling version directories (mirroring the actual `0.6.16`/`0.6.20` layout found on this machine) is required to catch exactly the class of defect found in this review; a same-directory-only test fixture would not have caught it.

**Scope note (open, not decided):** this needs to hook into `mcp-server/src/index.ts` (the tool-call entry point) to fire "on every call," but `index.ts` is also heavily rewritten by the unrelated, in-progress ADR-067/v0.7.0 KG-resolution work. The file overlap is real but the purposes are unrelated. Recommend this ships as its own separate plan, not folded into ADR-067's phase numbering, sequenced either onto its own branch or as a distinct commit sequence on `v0.7.0` after that branch's `index.ts` changes settle, to avoid conflicting edits. This sequencing decision has not been made — it is recorded here as open.
