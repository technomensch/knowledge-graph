# issue-49: Plan Safety-Header STATUS Field Frozen at Initial "STOPPED" — Never Rewritten on Approval or Completion

## Problem

Every implementation plan generated by `commands/kmg-start-issue-tracking.md` (Step 4.1,
Implementation Plan Template) is born with a hardcoded Safety Header:

```
**STATUS:** 🔴 STOPPED (Waiting for Manual Approval of Step 1)
```

Nothing in the downstream protocol ever rewrites this line. Verified live 2026-08-17 by auditing
five plans (`v0.7.1.1-issue-43`, `v0.7.1.2-issue-44`, `v0.7.1.3-ENH-060`, `v0.7.1.3-ENH-061`,
`v0.7.1.4-issue-45`) that were all fully implemented and merged (PRs #216, #218, #220, #223/#224
respectively) — every one still read the original "Waiting for Manual Approval of Step 1" text in
both `knowledge/plans/` and their `~/.claude/plans/` source copies. The staleness is not a
copy-sync artifact between the two locations; the field was never touched again after plan birth
in either copy.

## Root Cause

Two gaps stack:

1. **Template writes a placeholder once, at plan authoring time** — `kmg-start-issue-tracking.md`
   Step 4.1 hardcodes the STATUS line into every generated plan's Safety Header, with no
   corresponding instruction anywhere in that command to update it later.
2. **`kmg-execute-plan` skill's completion step doesn't write to the file** — Step 7
   ("Completion Verification") only requires the agent to "output completion status" to the
   conversation. Nothing in the skill's protocol edits the plan file's own STATUS line, whether at
   the Step-1-approval transition (STOPPED → IN PROGRESS) or at execution completion (→ COMPLETE).

The result: the Safety Header's STATUS field is decorative after the moment of plan creation —
it reflects nothing about the plan's actual lifecycle state, silently, for every plan this
project has ever generated via the full workflow.

## Relationship to ENH-052

This is a fifth instance of the pattern ENH-052 already named ("This Is the Same Pattern, One
Level Up" — a piece of internal documentation goes stale and nothing mechanically catches it),
alongside issue-13 (broken doc links), ENH-042 (version-sync, three disconnected partial
mechanisms), issue-26 (dead file reference in a command prompt), and issue-28 (hook gates built
but not wired to the live push path). It does not warrant a new ENH — it belongs under ENH-052's
existing "general enforcement mechanism, not another one-off fix" umbrella. See
[[ENH-052]] for the general pattern.

## Impact

- Any plan's STATUS field is unreliable for judging real progress — a reader (human or agent)
  scanning `knowledge/plans/` for what's actually in flight vs. done cannot trust the header at
  all; every plan reads "STOPPED, waiting for Step 1" regardless of true state.
- Silent: nothing surfaces the drift until a human manually cross-checks plan files against git
  history, as happened here.

## Blast Radius

Wider than it first looks — three separable pieces, all confirmed by the user 2026-08-17 as part
of this fix (own commit-group, c6, alongside c1-c5 in
`knowledge/plans/v0.7.1.5-orchestration-plan.md`):

1. **Prospective template fix** — `commands/kmg-start-issue-tracking.md` Step 4.1: stop hardcoding
   a single frozen STATUS string; the Safety Header needs to reflect real lifecycle states
   (awaiting approval / in progress / complete) going forward. PROTECTED file — needs the same
   explicit-permission gate any `commands/*.md` edit does.
2. **Protocol fix** — `skills/kmg-execute-plan/SKILL.md` Step 7 ("Completion Verification"): must
   actually write the plan file's STATUS line, not just narrate completion to chat. This is the
   piece that stops the bug from recurring on every future plan.
3. **Backfill for already-generated plans** — the five plans already found stale (and any others
   like them) won't self-heal from (1)/(2) alone, since those are prospective-only fixes. Per user
   decision, this needs a `kg_upgrade`-style backfix — but `kg_upgrade` as it exists today
   (`captureCorruptionDirs()` in `upgrade.ts`) only scans `sessions/decisions/lessons-learned`;
   `knowledge/plans/` is out of its scope by design (local-only, gitignored, not part of the KG
   content tree). This piece needs a **new** category (working name `plan-status-drift`) added to
   `upgrade.ts` — new inspect/apply functions scanning `knowledge/plans/*.md` (and optionally
   `~/.claude/plans/`) for the frozen Safety-Header pattern, same inspect+apply shape as
   `capture-corruption` but a different directory scope and a different corruption signature. This
   is real new surface in `upgrade.ts`, not a one-line fix — and it needs issue-51's wizard-routing
   fix to already be in place (or be built as part of this) for the new category to actually reach
   users through `/kmgraph:kmg-init`, rather than repeating issue-51's own gap on day one.

Files touched, best estimate: `commands/kmg-start-issue-tracking.md`, `skills/kmg-execute-plan/SKILL.md`,
`mcp-server/src/tools/upgrade.ts` (new category + tests in `mcp-server/tests/upgrade.test.ts`), and
the 5 already-known-stale plan files (manual one-time correction, already done for this session's
audit — see the session's prior status updates to `v0.7.1.1` through `v0.7.1.4` plans).

## Spec

1. Redesign the Safety Header to carry real states: e.g. `🔴 AWAITING APPROVAL` → `🟡 IN PROGRESS`
   → `✅ COMPLETE`, replacing the single frozen string in the Step 4.1 template.
2. `kmg-execute-plan` Step 1 (approval) writes the IN PROGRESS transition; Step 7 (completion)
   writes the COMPLETE transition — both to the actual plan file, not just to chat output.
3. New `upgrade.ts` category `plan-status-drift`: inspect scans `knowledge/plans/*.md` (excluding
   `archive/`) for the literal frozen-placeholder pattern in a plan whose branch shows as merged (a
   heuristic to avoid flagging genuinely-still-open plans); apply rewrites the STATUS line to
   `COMPLETE` with a note, conservative like `capture-corruption` — anything ambiguous (can't
   determine merge status) gets reported for manual review, not guessed.
4. Depends on issue-51 landing first (or being folded into this same commit-group) so the new
   category is actually reachable via the wizard — otherwise this repeats issue-51's exact bug for
   a brand-new category on day one.

**Effort:** Medium-to-Large — three separate files, one of them (`upgrade.ts`) requiring new
inspect/apply logic and test coverage, not a prose-only fix like issue-51. **Risk:** Medium — the
"which plans are actually done vs. still legitimately open" heuristic for the backfill piece needs
care (false-positive risk: don't mark a genuinely-stalled plan complete). Given this size, likely
does not fit as a trivial add to 7.1.5's existing scope without extending the timeline — worth
weighing against a dedicated 7.1.6, same question posed for issue-50/51.
