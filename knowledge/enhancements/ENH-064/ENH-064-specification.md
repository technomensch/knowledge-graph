# ENH-064: Attribution README for Initialized Knowledge Graphs

## Summary

When a knowledge graph is initialized (`kmg-init`), the resulting folder
(decisions, lessons, issues, enhancements, plans) currently carries no
marker explaining what created it or how to work with it. Add an
auto-generated README to the knowledge-graph folder at init time that
states the folder is maintained using KMGraph, and — for someone who
clones or forks the repo without the plugin installed — explains how to
install it and connect to the existing folder.

## Problem / Use Case

A maintainer installs KMGraph, uses it, and commits some of that content
(decisions, lessons, issues) into their own GitHub repo. Someone else
later clones or forks that repo. They see a folder of structured
Markdown files with no obvious system behind it: no explanation of what
the folder is, why it's organized this way, or that a companion tool
exists that unlocks search, capture, and guided creation against it.

Today there's nothing in the scaffolded structure that surfaces this.
The new user has no path from "found this folder" to "install the tool
that manages it."

## Proposed Solution

1. **`README.md` in the knowledge-graph folder root**, generated during
   `kmg-init` (and backfilled by `kmg-upgrade` for existing graphs missing
   one). Content, per this session's research and review:
   - States the files are plain Markdown, readable and editable without
     any tooling.
   - States the folder is maintained using KMGraph
     (https://kmgraph.stayinginsync.info) and that installing the plugin
     and running `/kmgraph:kmg-init` connects this folder to search,
     capture, and ADR/lesson/issue workflows.
   - Written in neutral, third-person voice. No em dashes (project style
     rule). No superlative/marketing language.
   - Colophon tone, not a pitch — answers "what is this folder" first,
     "how was it maintained" second. Modeled on existing prior art:
     Create React App's "bootstrapped with" README section,
     Renovate/Dependabot's "managed by" config-file comments, and
     terraform-docs/dbt's "generated by" watermark convention — all
     single-mention, link-once, no repeated branding.
2. **No per-file watermarking.** Do not stamp individual decision/lesson/
   issue files with attribution text or HTML comments — repeating a
   plugin badge across every content file reads as spam and pollutes
   files that may be copied elsewhere. One README is enough.
3. **Machine-detectable marker (open question, see below):** if
   `kmg-init` needs to detect "this folder already exists but wasn't
   initialized by me," a small config file (e.g. `.kmgraph.yml`) is a
   candidate — cleaner than parsing README prose. Needs design in the
   implementation phase; not decided here.

## Draft README Copy (subject to refinement during implementation)

> These files are plain Markdown. No tooling is required to read or edit
> them.
>
> This project's knowledge graph is managed by the KMGraph plugin
> (located at https://kmgraph.stayinginsync.info). Installing the plugin
> and running the `/kmgraph:kmg-init` command registers this folder as a
> local graph. This unlocks key features, including recall search across
> recorded decisions (ADRs), lessons learned, and issues, while also
> allowing users to create new entries.

## Research Notes (this session)

- Web search turned up no single "install companion plugin" convention
  specific to knowledge-management repos, but adjacent prior art is
  consistent: CRA/create-next-app write a one-time "bootstrapped with X"
  README section; Husky/Renovate/Dependabot drop a short "managed by X"
  comment in the config file they own; terraform-docs and dbt stamp a
  "generated by" watermark on generated output. Common thread: one
  mention, factual tone, no repeated branding.
- Model consultation (Fable, this session) recommended: explanatory
  colophon tone over either apologetic-hedging or directive-pitching;
  lead with what serves the reader (what is this, can I trust/edit it)
  before the provenance/install mention; frame the plugin as additive
  capability ("this unlocks X") rather than a deficiency ("you're
  missing X"); keep it to the README, not per-file markers.
- User revision (this session) tightened the draft to third-person/
  neutral voice and named the actual command (`/kmgraph:kmg-init`)
  instead of a generic instruction — see Draft README Copy above.

## Affected Files (implementation phase — none touched by this tracking pass)

- `kmg-init` command/skill (wherever it scaffolds a new graph — writes
  the new README)
- `kmg-upgrade` (backfill README for graphs initialized before this
  enhancement)
- `core/default-templates/` (PROTECTED — requires explicit user
  permission per `CLAUDE.md` Code Protection Rules) if the README is
  templated there rather than generated inline
- Possibly a new `.kmgraph.yml` marker file convention (open question)
- `INSTALL.md` and `docs/INSTALL.md` (kept in sync) — neither currently
  documents the "first-time install, pre-existing populated `knowledge/`
  folder" path this ENH creates; both only cover upgrading an existing
  KMGraph installation to a new version

## Out of Scope

- Per-file attribution/watermarking (explicitly rejected, see above)
- Marketing or promotional language of any kind
