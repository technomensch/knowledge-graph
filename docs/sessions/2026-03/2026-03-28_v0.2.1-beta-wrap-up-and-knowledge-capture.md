## Gaps Identified in start-issue-tracking

Two issues remain in the current `commands/start-issue-tracking.md` that were not addressed in v0.2.1-beta:

### Gap 1: Branch check timing
Step 1.0 runs `git branch -a` and reports the current branch as informational context. However, the **actual guard** (the three-option prompt) only fires at Step 5.0 — four steps later. If the user selected "create branch" during Step 1 discussions and moved on, they may have forgotten the context by Step 5.

**Impact:** Low risk but non-zero — the guard at Step 5 is the right place, but Step 1.0 should surface the non-main branch status visually so the user is primed before making decisions in Step 1.

### Gap 2: Lesson/ADR capture is optional
Step 6.2 asks: "Should I run `/kmgraph:capture-lesson` now?" — but the answer is optional. For issues being tracked during active implementation (the exact scenario that caused the ENH-001 branch contamination), the lesson about the problem should be captured before starting work, not offered as a suggestion.

**Suggested fix:** When `current_branch` is NOT main (Active Work Guard triggered), make Step 6.2 semi-mandatory for project-level issues: "This issue was identified during active implementation on [branch]. Capturing a lesson before starting is strongly recommended. Run `/kmgraph:capture-lesson` now? (yes / defer to plan)"

### Gap 3: Auto-lesson capture on file write not firing

**Feature advertised in v0.2.0 TL;DR:**
> "Running `/kmgraph:capture-lesson` does not need to be manually ran after breakthroughs. The tool now watches your file writes and automatically asks if something worth capturing just happened."

**Observed behavior:** The PostToolUse hook (`scripts/post-tool-lesson-check.sh`) is not triggering automatically after file writes. The user must still manually invoke `/kmgraph:capture-lesson` to document breakthroughs.

**Impact:** Medium — this was a core UX promise of v0.2.0-beta. The feature exists in the hook registry but is not firing as intended.

**Suggested fix:** Verify the `hooks/hooks.json` PostToolUse entry is correctly bound and that the shell script is executable. Likely needs investigation in v0.2.2.

### Gap 4: Notification webhooks lack user-facing setup documentation

**Feature advertised in v0.2.0 TL;DR:**
> "Notification webhooks are available (opt-in only). If you configure a Slack or webhook URL in your settings, you'll get notified when lessons or ADRs are saved. Off by default, no action needed."

**Observed gap:** No user-facing documentation exists explaining how to configure the webhook URL. Users who want to enable this feature have no documented path to do so.

**Impact:** Low (opt-in, off by default) — but the changelog advertises it as available, which creates a gap between promise and docs.
