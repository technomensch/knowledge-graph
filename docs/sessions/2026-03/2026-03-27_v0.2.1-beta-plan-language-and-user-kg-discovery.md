## Key Insights for Future Lessons & ADRs

### Lesson 1: Plan Language — "Create" vs "Update" Pattern

**Problem:** When writing plans, ambiguous language ("Update file X") for files that don't exist wastes context tokens. During execution, I would attempt to read the file, discover it doesn't exist, then wasted tokens determining if creation or modification was needed.

**Solution:** Explicit Create/Update distinction:
- **"Create `filename` (new file — does not exist)"** → unambiguous new file creation
- **"Update `filename`"** → clear modification of existing file

**When to apply:** Every implementation plan that creates or modifies files. The pattern prevents token waste and execution confusion.

**Related ADR needed:** Document the plan language convention for future cross-project reuse.

---

### Lesson 2: Workflow Discovery — "Add to Plan" vs "Start Issue Tracking"

**Problem:** When identifying new features or enhancements, I was offering informal suggestions ("Want me to add this to memory?" or suggesting `/kmgraph:start-issue-tracking` for everything) without considering whether the work belonged in an existing active plan.

**Solution:** Two-tier feature discovery:
1. **If feature relates to an active plan** → "Want me to add Phase N to [existing-plan]?"
   - More efficient when context and model assignments already exist
   - Keeps related work together
2. **If feature is standalone/deferred** → "Want me to start issue tracking for v0.2.2?"
   - Creates separate scope, branch, formal documentation
   - Better for cross-cutting or future-version concerns

**When to apply:** Every time a new feature/enhancement is identified during implementation work.

**Related ADR needed:** Document the decision-making tree for feature workflow (plan amendment vs issue creation).

---

### Lesson 3: Consistent Feedback Application in Multi-Phase Work

**Problem:** When user corrected approach mid-work (Phase 4 visibility issue), I corrected Phase 4 but allowed Phases 5-6 to continue with the old approach (background execution). This violated the correction without realizing it applied to all dependent work.

**Solution:** When a correction is made to execution approach mid-stream, stop and restart ALL parallel work using the old approach. Propagate corrections across all remaining phases, not just the immediate next task.

**When to apply:** Any multi-phase parallel work where user provides feedback about approach. Kill dependent work that violates the correction, respawn with the new approach.

**Related ADR needed:** Document decision-making for when to kill/restart parallel work vs when to continue with corrections.

    - Category: process
    - Save to: **global (user-level) KG** (applies to any project using subagents)
    - Problem: Foreground agents show nothing until final result; background agents send only completion/idle notifications. User has no way to distinguish "agent is working" from "agent is stuck/dead." Repeated incidents across v0.2.1-beta where agents appeared to hang with no feedback
    - Solution: Agents need periodic progress signals (heartbeat or status update) so users know work is happening. Until framework supports this, prefer direct foreground execution in main context for visibility-critical work
    - When to apply: Any multi-step agent task where user expects progress feedback
    - Context: Discovered during v0.2.1-beta Phase 7c (doc agents) and final validation review; user repeatedly asked "where is the feedback"
